# 미니 DBMS — 요구사항과 구현 정리

기준 : 2026-11-16 현재 코드와 README.
구현 언어 : Python 3.11 이상 / 화면 : JavaScript로 만든 미니 React.
목표 : SQL을 전달하면 데이터를 파일에 저장하고, B+ 트리로 ID를 찾으며, 외부 프로그램에서도 API로 사용할 수 있게 한다.

## 설계할 때 정해야 하는 내용

여러 프로그램이 같은 데이터를 쓰기 시작하면 동시성 문제, 검색 방법, 저장 실패 처리를 정교하게 설정해야 한다.
그 후 어떤 데이터를 다루고 각 기능이 어떤 상황에서 어떻게 동작할지까지 정해야 한다.

현재 구현 : 여러 프로그램이 DB 파일을 직접 수정하는 대신 하나의 DBMS 서버에 API 요청을 보낸다.
파일 관리 : 같은 데이터 폴더를 다른 DBMS가 동시에 열려고 하면 owner.lock으로 거부한다. 이 규칙을 무시하고 파일을 직접 수정하는 외부 프로그램까지 막는 OS 파일 잠금은 아니다.

## Phase 1 — SQL 파싱, 실행, 파일 저장

구현 목표 : SQL 문자열을 분석하고 INSERT, SELECT, UPDATE, DELETE를 실행한다.

파싱 : JavaScript나 외부 클라이언트에서 SQL문을 문자열로 전달하면 Python DBMS가 토큰으로 나누고 AST라는 구조화된 정보로 바꾼다.
실행 : AST를 기반으로 테이블, 컬럼, 값, ID를 검사한 뒤 명령을 수행한다.
데이터 저장 : INSERT, UPDATE, DELETE의 변경 내용을 transactions.jsonl 파일 끝에 로그로 추가한다.
데이터 조회 : B+ 트리에서 레코드와 파일 위치를 찾은 후 실제 파일을 읽어 결과를 반환한다.

예를 들어 아래 SELECT는 명령 SELECT / 테이블 products / 출력 컬럼 name, price / 조건 id = 42로 나뉜다.

| 동작 | SQL | 결과 |
| --- | --- | --- |
| 저장 | `INSERT INTO products (id, name, price) VALUES (42, '키보드', 30000);` | ID 42, 키보드, 30,000원 저장 |
| 조회 | `SELECT name, price FROM products WHERE id = 42;` | name과 price만 반환. ID는 검색 조건 |
| 수정 | `UPDATE products SET price = 35000 WHERE id = 42;` | ID 42의 가격을 35,000원으로 수정 |
| 삭제 | `DELETE FROM products WHERE id = 42;` | ID 42의 행을 제거 |

삭제 : 모든 컬럼을 NULL로 만드는 것이 아니라 행 자체를 제거한다. 다만 이전 로그는 파일에 남고 삭제 로그가 추가된다. 재시작할 때 삭제 로그까지 반영하여 해당 행을 복구하지 않는다.

지원 범위 : 단일 테이블 CRUD, WHERE의 동등 조건 1개, 여러 컬럼의 ORDER BY, LIMIT, 여러 행을 넣는 INSERT.
입력 방법 : 값은 SQL 문자열에 직접 이어 붙이기보다 ?와 params로 전달한다.
제한 : 요청당 SQL문 1개, SELECT 기본 100행·최대 1,000행, INSERT 최대 5,000행. UPDATE와 DELETE에는 WHERE id = 값이 필요하다.
저장 단위 : 하나의 INSERT에 여러 행을 넣으면 모두 성공하거나 모두 실패한다. 여러 SQL문을 묶는 BEGIN/COMMIT은 구현하지 않았다.

## Phase 2 — 메모리 기반 B+ 트리 인덱스

구현 목표 : 디스크 기반 B+ 트리를 단순화한 메모리 기반 방식으로 구현한다.
레코드에 ID를 부여하고 해당 ID를 B+ 트리에 등록하여 ID 검색에 활용한다.

자동 ID : INSERT에서 ID를 생략하면 자동으로 부여한다. ID 42를 직접 넣을 수도 있으며, 그 뒤 자동 ID는 43부터 시작한다.
ID 규칙 : 중복 ID는 거부하고 삭제된 ID는 자동 발급으로 재사용하지 않는다. UPDATE로 ID를 바꿀 수 없다.

트리 구조 : 내부 노드는 검색 방향을 정하고 리프 노드는 ID와 레코드 정보를 보관한다. 레코드 정보에는 현재 행과 로그의 파일 위치가 들어간다.
삽입 : 노드가 가득 차면 분할한다.
삭제 : 노드가 부족해지면 이웃에서 재분배하거나 병합한다.
순회 : 리프를 서로 연결하여 순서대로 읽을 수 있게 한다.

ID 검색 : WHERE id = 42 → B+ 트리 탐색 → 파일 위치 확인 → 해당 로그에서 행 읽기.
다른 조건 검색 : 이름·가격 같은 컬럼은 별도 인덱스가 없어 리프를 순회한다. 랭킹도 모든 후보를 확인하되 상위 LIMIT만큼만 보관한다.
재시작 : 파일 로그를 순서대로 읽어 B+ 트리, 다음 ID, 테이블 버전을 다시 만든다. 트리 자체를 디스크 페이지 형태로 저장하지는 않는다.

성능 요구사항 : 최소 100만 개 이상의 레코드를 INSERT하고 ID 조회와 재시작 복구가 가능한지 확인한다.

README에 기록된 측정 : 2026-11-14, Windows, Python 3.14.3. HTTP API로 1,000행씩 1,000회 저장했고 각 커밋마다 파일 동기화를 수행했다.

| 항목 | 기록된 결과 |
| --- | --- |
| 100만 행 INSERT | 21.69초 |
| 임의 ID 100회 조회 평균 | 10.72ms |
| 새 서버 시작 및 100만 행 복구 | 3.67초 |
| B+ 트리 높이 | 4 |
| 로그 파일 크기 | 94.16 MiB |

위 수치는 이전 환경에서 한 번 측정한 결과이다. 이번 정리에서 다시 측정한 값은 아니며, 100만 번의 개별 INSERT 성능을 의미하지 않는다.

## Phase 3 — 외부 클라이언트용 API 서버

구현 목표 : 구현한 API를 통해 외부 클라이언트에서 DBMS 기능을 사용할 수 있어야 한다.
Thread Pool을 구성하여 요청마다 스레드를 생성하고 삭제하는 비용을 줄인다.

현재 구현 : Python HTTP 서버와 ThreadPoolExecutor를 사용한다. 기본 Worker는 4개이며 1~16개로 설정할 수 있다.
요청 제한 : 추가 대기는 최대 128개이고 처리 여유가 없으면 503을 반환한다. JSON 본문은 최대 1.2 MB이다.
외부 클라이언트 : 브라우저, curl, PowerShell, 다른 프로그램에서 HTTP JSON으로 요청할 수 있다.

| API | 동작 |
| --- | --- |
| POST /api/sql | SQL 실행. sql, params, expectedVersion을 전달 |
| GET /api/db/stats | 행 수, 다음 ID, 버전, B+ 트리 높이, 충돌·조회·스레드 풀 통계 |
| GET /api/challenge | 도전 분류와 생성 규칙 조회 |
| POST /api/challenge/start | 랜덤 배치와 도전 ID 발급. restartAttemptId가 있으면 같은 배치 재시작 |
| POST /api/challenge/finish | 클릭 기록을 검사하고 성공 여부·이동 횟수·소요 시간 확정 |
| POST /api/records | 성공이 확인된 도전의 닉네임과 기록 저장 |
| GET /api/puzzles/challenge-01/ranking | 랭킹 상위 10개 조회 |

SQL 요청 예시 :
```json
{
  "sql": "INSERT INTO products (name, price) VALUES (?, ?)",
  "params": ["키보드", 30000]
}
```

조회 응답 : rows, version, plan, scanned.
변경 응답 : affectedRows, ids, version.
기본 주소 : http://127.0.0.1:4173. 같은 PC의 별도 프로그램도 외부 클라이언트이다. 다른 PC의 접속은 HOST와 방화벽 설정이 별도로 필요하다.

## 데이터 구조

products : CRUD와 인덱스 실험에 사용하는 상품 테이블.
- id : 양의 안전한 정수, 생략하면 자동 부여.
- name : 공백만 있는 값은 불가, 1~200자.
- price : 0 이상의 유한 숫자.

records : 퍼즐 성공 기록을 저장하는 테이블.
- id : 자동 부여하는 기록 ID.
- puzzle_id : 도전 분류 ID. 현재 challenge-01.
- nickname : 앞뒤 공백을 제거한 1~20자.
- moves : 검증된 해답 경로의 이동 횟수, 1~1,000.
- elapsed_ms : 서버에서 측정한 시간. 밀리초 정수로 저장하고 화면에서는 초 단위로 표시.
- created_at : 서버에서 생성하는 UTC 등록 시각.

기존 시간 미측정 기록 : elapsed_ms를 NULL로 읽고 화면에는 시간 미측정으로 표시한다.
스키마 : 두 테이블을 Python 코드로 정의했다. CREATE TABLE은 지원하지 않는다.
기록 보호 : records는 /api/sql에서 조회만 가능하고 변경 요청은 403으로 거부한다. 기록 등록은 성공 검증 API를 거친다.

## 동시성 제어 — 적합성 검증과 Lock

구현 목표 : 동시에 저장·수정·삭제·조회가 들어와도 중간 상태나 잘못된 파일 위치를 읽지 않게 한다.

적합성 검증 : 변경 계획을 만들 때 테이블 버전을 읽고, 커밋 직전에 현재 버전과 다시 비교한다. 이를 낙관적 동시성 제어(OCC)라고 한다.
일반 요청 : 그 사이 버전이 바뀌면 최신 상태를 기준으로 변경 계획을 다시 만든다.
버전 지정 요청 : 클라이언트가 expectedVersion을 전달했고 현재 버전과 다르면 409로 거부한다.

예시 : A와 B가 모두 버전 3을 조회한 뒤 A가 수정하여 버전 4가 되었다. B가 expectedVersion: 3으로 수정하려 하면 충돌로 처리한다. B는 다시 조회하고 계산한 뒤 요청해야 한다.
주의 : expectedVersion 없이 같은 행을 수정하면 나중에 처리된 값이 남을 수 있다. 검증은 행이 아니라 테이블 단위라 서로 다른 행의 변경도 충돌할 수 있다.

Lock : 커밋 Lock으로 쓰기 확정을 한 번에 하나씩 처리한다.
RLock : B+ 트리와 메타데이터를 탐색·수정하는 구간을 보호한다.
조회 : 확정된 레코드와 파일 위치의 스냅샷을 잡고 각자 별도 파일 핸들로 읽는다.

수정·삭제 중 조회가 반드시 오류를 내는 것은 아니다. 현재 코드는 확정된 스냅샷과 변경 로그를 사용하므로 조회를 시작한 시점의 기존 값을 안전하게 읽을 수 있다.

## 저장 실패와 복구

정상 저장 : 값 검증 → 변경 계획 → 커밋 잠금·버전 재검사 → 로그 추가 → flush와 fsync → 메모리·B+ 트리 반영 → 성공 응답.

저장 실패 : 일부 쓰기나 fsync가 실패하면 파일을 직전 크기로 되돌리고 메모리·인덱스·다음 ID를 확정하지 않는다.
되돌리기 실패 : 이후 쓰기를 중단하고 오류를 반환한다.
비정상 종료 : 마지막 로그 줄이 미완성이면 그 꼬리만 제거한다.
파일 손상 : 완성된 로그의 체크섬이 틀리면 원본을 보존하고 서버 시작을 거부한다.
정상 종료 : 진행 중인 DB 작업이 끝날 때까지 기다린 뒤 파일과 소유권 잠금을 정리한다.

| 상황 | 응답 |
| --- | --- |
| 잘못된 SQL·컬럼·값 | 400 |
| records 직접 변경 | 403 |
| 존재하지 않는 ID 조회·수정·삭제 | 404 |
| 중복 ID·버전 충돌·성공 확인 전 기록 저장 | 409 |
| 만료되거나 현재 서버에 없는 도전 ID | 410 |
| 저장 실패·처리 용량 초과 | 503 |
| 저장 파일 손상 | 복구 또는 읽기 단계에서 오류 처리 |

조회 규칙 : 없는 ID를 지정한 SELECT는 404이다. 다른 컬럼 조건에 맞는 행이 없으면 빈 결과를 반환한다.

## 퍼즐 페이지와 DBMS 연결

구현 목표 : 퍼즐 플레이 → 성공 검증 → 기록 저장 → 랭킹 조회까지 연결한다.

공통 도전 : 서버가 꺼진 보드에서 무작위로 서로 다른 5칸을 눌러 시작 배치를 만든다. 따라서 풀 수 있는 배치이며 매번 같은 보드는 아니다.
타이머 : 서버의 도전 발급부터 성공 확인 요청을 받기까지 측정한다. 닉네임 입력 시간은 제외하지만 통신 지연은 포함된다.
성공 검증 : 클라이언트의 점수를 그대로 믿지 않고 시작 배치에 클릭 기록을 적용하여 모든 불이 꺼지는지 확인한다.
중복 처리 : 같은 도전·같은 해답의 성공 확인과 같은 닉네임의 기록 저장을 재요청하면 기존 결과를 돌려준다.

저장 : 검증한 이동 횟수와 소요 시간, 닉네임을 records에 INSERT한다.
랭킹 : 이동 횟수 → 소요 시간 → 등록 시각 → ID 오름차순으로 상위 10개를 조회한다. 같은 이동 횟수라면 빨리 푼 기록이 먼저 나온다.
이전 기록 : 같은 이동 횟수에서 시간 미측정 기록은 측정된 기록 뒤에 나온다.
새로고침 : 같은 서버 실행 동안 진행 보드·도전 ID·타이머를 브라우저 저장소에서 복원한다.
서버 재시작 : 진행 중 도전은 초기화하지만 DB 파일에 등록한 랭킹은 유지한다.
도전 세션 : 서버 메모리에서 최대 4,096개, 24시간 유지한다. 랭킹은 세션과 별도로 파일에 저장한다.

## Phase 1, 2, 3 전체 흐름

```text
외부 클라이언트
  → HTTP API와 Thread Pool                         [Phase 3]
  → SQL 문자열 파싱과 실행 계획                    [Phase 1]
  → ID 확인과 B+ 트리 탐색                         [Phase 2]
  → 버전 검증·잠금·파일 로그 저장 또는 파일 조회
  → JSON 결과 반환
  → 미니 React 상태 변경
  → 새 VDOM 생성 → Diff → 바뀐 DOM만 Patch
```

세 단계가 따로 실행되는 예제가 아니라 하나의 요청 처리 과정으로 연결되어 있다.
게임 기록 API는 서버 내부에서 SQL을 생성하여 같은 실행기·파일 저장·인덱스를 사용한다.

제약 : 데이터와 로그가 늘면 메모리·디스크 사용량도 늘어난다. Thread Pool은 요청 처리 스레드를 재사용하지만 CPU 연산이 스레드 수만큼 빨라진다는 의미는 아니다.
