# 미니 레디스 (C)

외부에서 SET / GET / DEL 을 쓸 수 있는 키-값 데이터 저장소 서버. 해시 테이블을 직접 구현했다.

크래프톤 정글 13기 · 2026-11

## 1. 무엇을 만들었나

- 레디스처럼 **APP이 소켓으로 명령 한 줄을 보내면 답 한 줄을 돌려주는** 서버
- 명령: `SET key value`, `SET key value EX 초`, `GET key`, `DEL key`
- 답: `OK`, 값, `(nil)`, `1`/`0`, `(error) 이유`

```
SET 날씨 "맑은 하늘" EX 60   → OK
GET 날씨                     → 맑은 하늘
DEL 날씨                     → 1
GET 날씨                     → (nil)
HELLO                        → (error) 모르는 명령
```

## 2. 구조

```
APP 프로세스  ⇄  OS(소켓)  ⇄  레디스 서버 프로세스
                               ┌─────────────────────────────────────────┐
                               │ 3층 네트워크   server.c     글자를 주고받음 │
                               │ 2층 명령       command.c    자르고 검사     │
                               │ 1층 해시 테이블 hashtable.c  저장·조회·삭제  │
                               └─────────────────────────────────────────┘
```

- 층마다 **바로 아래 층과 함수 하나로만** 대화한다 (계층화).
  - 3층 → 2층: `execute_line(t, "SET 날씨 맑음")` → `"OK"` (글자를 넣으면 글자가 나온다)
  - 2층 → 1층: `ht_set(t, "날씨", "맑음")`
- 그래서 층마다 따로 테스트했고, 2층을 테스트하던 코드를 진짜 소켓으로 갈아 끼워 3층을 얹었다.

서버의 루프는 두 겹이다.

```
바깥 루프 (서버가 꺼질 때까지)
│  ① accept: APP 연결 기다리기 (잠듦)
│  안쪽 루프 (그 APP이 연결된 동안)
│  │  ② read: 한 줄 읽기 (잠듦). 0글자 = APP이 끊음 → 탈출
│  │  ③ execute_line
│  │  ④ write: 답 보내기
│  └  ⑤ ②로
└  close → ①로
```

## 3. 해시 테이블

```
buckets[0] = NULL
buckets[1] ──▶ [날씨 | 맑음] ──▶ NULL
buckets[2] = NULL
buckets[3] ──▶ [이름 | 진훈] ──▶ [나이 | 30] ──▶ NULL     (충돌 → 체인)
```

- **연결 리스트 n개가 있고, 각 연결 리스트에서 첫 노드의 주소를 배열(`buckets`)에 담는다.**
- 노드(`entry`) = key, value, 만료 시각(`expire_at`), 다음 노드(`next`)
- **해시 함수: key → 배열 칸 번호(0 ~ n-1).** 같은 key는 항상 같은 번호라서, n개 리스트를 다 뒤지지 않고 한 리스트로 바로 간다. 다른 key가 같은 번호를 받으면(충돌) 그 리스트에 노드를 이어 붙인다(체이닝).
- GET / SET / DEL은 "칸 고르기(해시 함수) → 리스트 따라가며 key 비교"를 함께 쓴다 (`find`).
- key와 value는 **깊은 복사**로 저장한다. 넘겨받은 글자는 명령 하나가 끝나면 버려지기 때문이다. 얕은 복사로 바꾸면 댕글링 포인터가 되어 AddressSanitizer가 `heap-use-after-free`로 서버를 멈추는 것을 실험으로 확인했다.

## 4. 만료

- `SET 날씨 맑음 EX 60` → 노드의 `expire_at` = 지금 + 60초
- **GET 할 때 확인한다 (lazy expiration).** 노드를 찾은 뒤 값을 돌려주기 전에 `expire_at`과 지금 시각을 비교하고, 지났으면 그 노드를 리스트에서 빼고 메모리를 돌려준 뒤 `(nil)`로 답한다. DEL, SET도 같은 규칙을 따른다 (만료된 것은 없는 것).
- 무효화(데이터가 바뀜)는 APP이 `DEL`로 한다. 만료(시간)는 레디스가 알아서 한다.

## 5. 성능 비교

느린 API 서버(답하기 전에 1초 쉼)를 원본으로 두고, APP이 같은 요청을 10번 보냈다.

| | 레디스 없이 | 레디스 쓰고 (cache-aside) |
|---|---|---|
| 10번 합계 | 10,011 ms | 약 1,009 ms |
| 요청 1번 | 매번 약 1,001 ms | 첫 번째(miss) 1,003 ms, 나머지 9번(hit) 약 0.6 ms |

- 둘 다 최초에는 원본에서 읽어 와야 한다. 레디스가 없으면 나머지 9번도 똑같이 원본에 다녀오고, 레디스가 있으면 나머지 9번은 레디스 서버에 소켓으로 물어 0.6 ms 만에 받는다.
- 측정하다 발견한 것: 처음엔 hit 한 번이 약 44 ms였다. 서버가 답을 두 번에 나눠 보내서(`값`, `\r\n`) OS가 매번 약 40 ms씩 기다렸기 때문이다. 한 번에 보내게 고치니 0.6 ms가 됐다.

## 6. 한계

- **스레드 1개, 연결 1개씩.** 해시 테이블을 만지는 스레드가 하나라 동시성 문제(락)는 없다. 대신 지금은 한 APP의 연결이 끊길 때까지 그 연결의 read에 붙잡혀 있어서, 다른 APP이 연결하면 accept 대기열에서 기다린다 (측정 중 실제로 겪음). 진짜 레디스는 epoll로 여러 연결 중 글자가 온 것만 골라 처리한다.
- **만료는 GET할 때만 확인한다.** 아무도 찾지 않는 만료된 노드는 메모리에 남는다. 진짜 레디스는 주기적인 청소도 같이 한다.
- **서버가 꺼지면 데이터가 휘발된다.** 스냅샷이나 명령 로그로 디스크에 남기는 기능(선택 과제)은 만들지 않았다.
- 리사이즈 없음: 노드가 많아지면 리스트가 길어져 느려진다.

## 실행 방법

WSL Ubuntu, gcc, make. 모든 빌드는 `-Wall -Wextra -Werror` + AddressSanitizer/UBSan.

```bash
make test                 # 단위 테스트: 해시 테이블 26개, 명령 32개

make server && ./build/server        # 터미널 A: 레디스 서버 (127.0.0.1:6379)
nc 127.0.0.1 6379                    # 터미널 B: 손으로 명령 보내기

make slow_api && ./build/slow_api    # 터미널 B: 느린 API 서버 (127.0.0.1:8000)
make bench && ./build/bench          # 터미널 C: 성능 비교
```

## 파일

| 파일 | 역할 |
|---|---|
| `src/hashtable.{h,c}` | 1층 해시 테이블 (ht_set, ht_set_ex, ht_get, ht_del, 만료) |
| `src/command.{h,c}` | 2층 명령 한 줄 → 자르기 → 검사 → 해시 테이블 호출 → 답 한 줄 |
| `src/server.c` | 3층 소켓 서버 (accept / read / write 루프) |
| `src/slow_api.c` | 성능 비교용 느린 원본 API 서버 |
| `src/bench.c` | 성능 비교용 APP (cache-aside) |
| `tests/test_hashtable.c` | 1층 단위 테스트 |
| `tests/test_command.c` | 2층 단위 테스트 (명령 형식, 에러, 만료) |
| `Makefile` | 빌드·테스트 순서표 |
| `docs/` | 과제 원문, 진행 기록, 블로그 |
