## 진훈이 정리한 것 ✅
- 서버는 실행되면 요청을 기다리다가, 요청이 오면 정해진 약속대로 응답한다
- "기대값 → 실행 → 비교"라는 사고방식을 훈련한다 (이번 프로젝트의 개인 목표)
- 성능 비교에서는 첫 요청과 반복 요청을 따로 잰다 (첫 요청은 원본 + 보관함에 넣기라서 오히려 느리다)
- 레디스 값이 비어 있을 때(처음이거나, 만료·무효화됐을 때)는 원본에 다녀온다
- 요청 흐름 두 갈래 (진훈 백지 → 고쳐 그림)
  - i) APP 요청 → 레디스에 해당 데이터 있음 → APP이 데이터 갖고 옴
  - ii) APP 요청 → 레디스에 해당 데이터 없음 → APP이 DB에서 해당 데이터 읽고, 레디스에 저장
- "레디스 서버의 창구" = API
- 해시 테이블: 서랍장은 배열, 서랍 N개. 해시 함수는 key를 넣으면 몇 번째 서랍인지 계산한다
- 충돌은 막을 수 없다 → 체이닝: 같은 서랍의 쪽지를 연결 리스트로 잇는다
- C에서 key, value는 둘 다 주소다 (글자 길이가 제각각이라)
- GET/SET/DEL 공통: 1. 서랍 고르기(해시 함수, % N) 2. 줄 걷기(next 따라 이름 비교) → 하나의 함수로 만들어 셋이 같이 쓴다
- SET에 같은 이름이 이미 있으면 값만 바꾼다 (같은 이름 쪽지는 한 장만)
- DEL에서 맨 앞 쪽지를 지울 때는 서랍의 화살표를 바꾼다
- B 창구: (해시 테이블을 만지는) 스레드는 1개다. 그래서 동기화 문제가 발생하지 않는다. 약점은 여러 요청이 왔을 때 순차적으로 처리하기 때문에, 앞의 요청이 해결되어야 뒤의 요청이 해결된다는 것이다. → 그래서 명령 하나하나를 짧게 유지한다
- 해시 테이블을 read/write 하는 스레드가 1개
- C 만료: 기한 지난 쪽지를 GET하면 → 쪽지 버림, 레디스는 "없음"이라고 답함 (→ 손님은 원본에 다녀오는 ii 갈래로)
- 만료 처리 두 방법(꺼낼 때 확인 / 가끔 청소) 중 "가끔 청소"는 가비지 컬렉터와 닮았다 (진훈 발견)
- 이번 과제의 만료 처리는 "꺼낼 때 확인"만으로 충분하다 (원문: "요청받았을 때")
- C 무효화: DB만 고치고 레디스를 안 건드리면 레디스는 옛 값을 준다 → DB 고칠 때 DEL로 쪽지를 지운다 → 다음 GET은 "없음" → 손님이 DB에서 읽고, 레디스에 저장 → 손님이 새 데이터를 씀
- C 한 줄 정리: 만료는 시간 때문에, 레디스가 알아서 지운다. 무효화는 DB 때문에, APP이 지운다. (고리: 만료 = 유통기한, 무효화 = 리콜)
- D 다운 대비: 서버가 꺼지면 메모리의 데이터는 휘발된다. 대비하는 2가지 방법이 있다.
  - 스냅샷: 주기적으로 레디스의 모든 데이터를 디스크에 저장한다. 서버가 켜지면 디스크의 해당 데이터를 복원한다. 마지막 세이브 이후의 데이터는 여전히 리스크가 남아 있다.
  - 로그: 레디스가 수정될 때마다 해당 명령을 디스크에 저장한다. 파일을 처음부터 다시 실행해서 재현할 수 있다. 명령을 하나하나 실행하면서 재현하기에 서버가 다시 켜지면 느리다.
- E 손님 + 원본: 느린 원본을 만들어서, 레디스를 쓸 때와 안 쓸 때의 응답 시간(요청을 보내고 값을 받기까지 걸린 시간)을 측정 비교한다
  - 기대값: 원본 1초, 레디스 0초, 10번 요청 → 레디스 없이 1초 × 10번 = 10초 / 레디스 쓰고 1초 + 0초 × 9번 = 1초
- 프로세스 간에는 격리되어 있어서 각자의 메모리를 read/write 할 수 없다. 즉, 레디스 서버와 APP은 운영체제를 매개해야 한다

## 엣지 케이스 테스트 후보 (원문: "엣지 케이스를 최대한 고려")
- DEL로 없는 key를 지우면 → 아무것도 안 바뀌고 "0개 지웠음"
- DEL로 줄 맨 앞 쪽지를 지우면 → 서랍의 화살표가 다음 쪽지를 가리킨다 (버그 잘 나는 자리)
- SET으로 이미 있는 key를 저장하면 → 쪽지가 늘지 않고 값만 바뀐다
- GET으로 없는 key를 찾으면 → "없음"
- 같은 서랍에 여러 key가 충돌해도 → 각자 자기 값을 찾는다

- ~~언어~~ → **C로 결정** (진훈, 11/13): JS보다 C에 익숙해지고 싶고, 실제 레디스 서버가 C 프로그램이라서. 실행 환경은 WSL Ubuntu (gcc 13, make 있음)
- 명령 형식 → **한 줄에 명령 하나, 띄어쓰기로 자름, 값에 띄어쓰기가 있으면 따옴표로 묶음** (진훈 결정 "규칙 B", 따옴표 자르기 규칙은 ❔ → 동작 테스트로 확인)
  - 0번째 = 명령, 1번째 = key, 2번째 = value (진훈 ✅)
  - `SET 날씨 맑음` → OK · `SET 날씨 "맑은 하늘" EX 60` → OK (60초 뒤 만료) · `GET 날씨` → 값 / (nil) · `DEL 날씨` → 1 / 0
  - 규칙 A("2번째부터 전부 값")는 EX 60까지 값에 먹혀서 버림 (진훈 레드팀)
- 이상한 입력 → 공통 규칙: **약속을 어기면 `(error) 이유`로 답하고, 보관함은 건드리지 않는다. 서버는 죽지 않고 다음 요청을 받는다** (Claude 제안, 진훈 승인. 기대값 ❔ — 실행해서 확인 전)
  - `GET` → (error) key가 없음 · `SET 날씨` → (error) value가 없음 · `HELLO 날씨` → (error) 모르는 명령
  - `set 날씨 맑음` → OK (대소문자 안 가림) · `SET 날씨 "맑은 하늘` → (error) 따옴표가 안 닫힘
  - 추가 후보: `SET 날씨 맑음 EX abc` / `EX -5` / `EX` 뒤 숫자 없음 → (error) 만료 시간이 잘못됨
- 요령 (진훈이 "수고로운 사고방식"이라 한 것에 대한 답): 예외는 규칙 하나로 묶고, 검사는 B 창구에서 전부 해서 A 보관함에는 깨끗한 입력만 들어가게 한다
