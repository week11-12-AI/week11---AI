어제는 코드 없이 큰 그림만 그렸다. 오늘은 계단을 하나씩 올라갔다. **해시 테이블(계단 1) → 명령 자르기(계단 2) → 네트워크 큰 그림(계단 3)**.

## 1. 아침: "AI 슬롭"을 만들지 않는 규칙

친구가 보낸 글의 요지: **슬롭 = 만드는 데 든 노력보다 이해하는 데 드는 노력이 더 큰 결과물.** AI가 코드를 빨리 써도 검토 비용은 줄지 않는다. 이해 못 한 코드를 쌓는 건 카드 결제와 같다. 언젠가 갚아야 한다.

내가 채택한 규칙 ✅
1. AI가 한 번에 쓰는 코드 양을 줄인다. 계단 하나 = 함수 몇 개.
2. 같은 실수는 기계가 잡게 한다. 컴파일 경고는 전부 에러로(`-Wall -Wextra -Werror`), 메모리 실수는 검사기(AddressSanitizer)로.
3. ❔를 오래 두지 않는다. 계단이 끝날 때마다 실행해서 ✅ / ❌로 판정한다.

## 2. 계단 1: 해시 테이블

`ht_set` / `ht_get` / `ht_del`을 C로 만들고 단위 테스트 19개로 확인했다.

내가 정한 기대값 ✅: 서랍 1개에 김철수를 두 번 SET(010-1 → 010-9), 김영희를 DEL 하면
→ GET 김철수 = 010-9, GET 김영희 = 없음, DEL 박지성 = 0

직접 확인한 것 ✅
- `make test`를 내가 직접 돌려서 19개 통과를 봤다. AI가 "통과했다"고 한 말을 그대로 믿지 않았다.
- **검사기가 진짜 잡는지 일부러 깨 봤다.** `ht_free`를 주석 처리 → 메모리 누수 보고가 뜸 → 되돌리고 전부 통과.
- **깊은 복사 실험**: 값을 복사하지 않고 주소만 저장하게 바꿔 봤다 → 덮어쓰기 때 남의 메모리를 free 하다가 프로그램이 죽었다 → 되돌림.

find(서랍 고르고 줄 걷기) 설명 ✅
1. key로 서랍 번호를 계산하고(해시 함수 → % n), 그 서랍의 첫 쪽지 주소를 e에 넣는다.
2. 쪽지가 있는 동안
3. 쪽지 이름(e->key)과 찾는 이름(key)이 같으면 멈춘다.
4. 아니면 e를 다음 쪽지로 옮긴다.
5. e를 돌려준다. 찾았으면 쪽지, 줄 끝까지 갔으면 NULL.

알아차린 것: 테스트가 다 통과하니 **"AI가 어련히 잘했겠지"** 하고 넘어가고 싶었다. 인지적 항복이다. 대책은 전부 검토가 아니라 두 개만 하는 것이다. "이상한 입력이 오면?" 하나, "일부러 깨 보기" 하나.

## 3. 계단 2: 명령 자르기 + 검사

APP이 보낸 글자 한 줄 `SET 날씨 "맑은 하늘"`을 조각내서 해시 테이블 함수를 부르고, 답 글자를 만든다. 이 일을 하는 함수가 `execute_line`이다.

- **입력 → 출력**: 명령 한 줄(글자) → 답 한 줄(글자). 예: `"GET 날씨"` → `"맑음"`
- 안에서 하는 일: 자르기 → 검사 → 해시 테이블 함수 호출 → 답 만들기

자르기 설명 ✅
`SET 날씨 "맑은 하늘"` → 3조각 `["SET", "날씨", "맑은 하늘"]`. 따옴표 안의 띄어쓰기는 글자로 취급하고, 따옴표 자체는 버린다.

기대값 20개 ✅: 내가 10개를 정했고(SET/GET/DEL, 소문자, 에러 3종), AI가 제안한 10개(띄어쓰기 여러 개, 빈 값, 줄 끝 `\r\n` 등)에 하나씩 O/X를 줬다. 직접 `make test` → 20개 통과.

깨달은 것 ✅: **내가 O/X를 판정한 것 = 기대값을 설정한 것**이다. 코드가 그렇게 도는지는 실행해야 안다.

### 처음 보는 문제에서 요구사항은 어떻게 정하나 ❔

"빈 값을 허용할까?" 같은 걸 매번 고민하면 끝이 없다. 기준 네 개로 판단한다.
- **목적**: 과제가 원하는 게 뭔가
- **선례**: 진짜 레디스는 어떻게 하나 (AI가 찾고, 내가 고른다)
- **일관성**: 다른 규칙과 부딪히지 않나
- **되돌리기 비용**: 나중에 바꾸기 쉬운 결정(양방향 문)은 빨리 정하고 테스트로 기록한다. 바꾸기 어려운 결정(한 방향 문)만 오래 고민한다.

## 4. 계단 3: 네트워크의 큰 그림

과제 원문: "저장소는 **외부에서 사용할 수 있어야** 합니다." 지금까지는 테스트 코드가 같은 프로그램 안에서 `execute_line`을 불렀다. 이제 다른 프로그램(APP)이 부를 수 있게 만든다.

### 큰 그림 ✅

```
APP 프로세스  <->  OS(소켓)  <->  레디스 서버 프로세스
                                   └ 데이터(해시 테이블)를 자기 메모리에 들고 있음
```
두 프로세스는 서로의 메모리를 못 본다(프로세스 격리). 그래서 OS를 거쳐 주고받는다.

### 계층화: 층마다 바로 아래 층과 문 하나로만 대화한다

```
계단 5  APP + 느린 원본 API + 성능 비교
계단 3  네트워크 (소켓)          ── "SET 날씨 맑음" ──▶ / ◀── "OK"
계단 2  명령 (execute_line) ✅   ── key, value ──▶ / ◀── 성공·값
계단 1  해시 테이블 (ht_*)  ✅
```
- 소켓도 글자를 주고 글자를 원한다. `execute_line`은 글자가 테스트 코드에서 왔는지 소켓에서 왔는지 모른다. 그래서 계단 1·2를 건드리지 않고 계단 3을 얹을 수 있다. **테스트 코드는 가짜 소켓이었다.**
- 이점: 갈아 끼우기 / 층마다 따로 검증 / 버그 위치 좁히기 (아래 층은 테스트로 확인했으니 새 층부터 의심한다)
- PintOS에서 본 것과 같다: 유저 프로그램 ──write(fd)──▶ 시스템 콜 ──▶ 커널. 유저 프로그램은 문만 안다.

### 소켓과 버퍼

- **소켓** = OS가 만들어 주는 통로. 프로그램은 이걸 **번호(fd)**로 받는다. PintOS의 `open()`이 돌려주던 fd와 같다. 그래서 `read(fd)` / `write(fd)`로 다룬다.
- **버퍼** = 통로 안에서 글자가 잠깐 기다리는 OS 메모리. **방향마다 따로** 있다(서버가 읽을 것 / APP이 읽을 것).

내가 정리한 것 ✅
- 줄 끝 `\r\n`은 **명령이 어디서 끝나는지 알리는 약속**이다. 소켓으로 오는 글자에는 경계가 없어서 필요하다. APP도 서버도 `\r\n`으로 끝낸다. 이런 약속을 **프로토콜**이라고 한다.
- 서버의 읽기 칸(buf)은 다음 명령이 오면 덮어써진다. 그래도 해시 테이블에는 **깊은 복사로 만든 사본**이 있어서 문제없다. ❔ → 계단 3 구현 후 얕은 복사로 깨 보는 실험으로 확정할 예정. (계단 1에서 남긴 "깊은 복사는 왜 꼭 필요한가"의 답이 여기 있었다.)

### 서버의 루프는 두 겹이다 ✅

```
바깥 루프 (서버가 꺼질 때까지 영원히, Ctrl+C로 끔)
│  ① APP 연결 기다리기
│
│  안쪽 루프 (이 APP이 연결을 유지하는 동안)
│  │  ② 한 줄 읽기  ── APP이 연결을 끊었으면(read가 0글자) → 안쪽 루프 탈출
│  │  ③ execute_line
│  │  ④ 답 보내기
│  └  ⑤ ②로
│
└  연결 닫기 → ①로 (다음 APP 기다리기)
```
내 말로 ✅: ①은 APP과 서버가 연결될 때 한 번, ②~⑤는 APP이 명령 줄을 보낼 때마다 한 바퀴.

### 틀렸다가 고친 것

질문: APP 1이 `SET 날씨 맑음`을 보내고 연결을 끊었다. 새 APP 2가 `GET 날씨`를 보내면?
- 내 처음 답: nil ❌ (끊으면 ③이 실행 안 되니까)
- 정답: **맑음**. ③(SET)은 끊기 **전에** 이미 끝났다. 해시 테이블은 서버 프로세스의 메모리에 있어서 APP이 끊어도 남는다. 그래서 레디스가 **여러 APP이 같이 쓰는 저장소**가 된다.

```
APP 1:  연결 ── SET 날씨 맑음 ── OK ── 끊음
서버:     ①    ② ③ht_set ④     ②(0글자 → 탈출) → ①
테이블:  (빔) → [날씨=맑음] ─────────────▶ 계속 남음
APP 2:                              연결 ── GET 날씨 ── "맑음"
```

데이터가 사라지는 때 ✅
| 언제 | 누가 | 계단 |
|---|---|---|
| `DEL 날씨` | APP이 직접 (무효화) | 2 |
| 서버가 꺼질 때 | 메모리 **휘발** | 3 |
| `EX 60` 기한이 지나면 | 레디스가 (만료) | 4 |

### 계단 3 기대값 (실행은 다음 출근 때)

```
[APP 1]  SET 날씨 맑음 → OK      GET 날씨 → 맑음
[APP 2]  GET 날씨 → 맑음         DEL 날씨 → 1        GET 날씨 → nil
[서버 재시작, APP 3]  GET 날씨 → nil
```
서버 코드(`server.c`)는 AI가 써 뒀다. ❔ 내가 직접 실행해서 비교하기 전이다.

## 5. 곁가지: 주장을 주고받는 법

지인과 "AI 모델에 칩의 흔적이 남는다"로 언쟁이 있었다. 찾아보니 **같은 모델이라도 어떤 GPU에서 돌렸느냐에 따라 출력이 미세하게 달라지고, 그걸로 칩을 추정할 수 있다**는 학회 논문(ICML 2025)이 있었다. 지인의 "근거 없는 헛소리"는 틀렸다. 그런데 나도 "모델에 흔적이 남는다"는 모호한 표현에 출처 없이 전달했다.
- 주장을 공유할 땐 **출처 + 정확히 무엇을 주장하는지 한 문장**을 같이.
- 상대 말에서 쓸 건 가져간다: 지금 목표와 상관없는 정보에 주의력을 쓰지 말 것.

## 6. 오늘 배운 일하는 방법

- **처음 보는 개념은 "보기 → 따라 말하기 → 기대값" 순서.** 소켓을 보기도 전에 기대값부터 물었더니 막막하고 거부감이 들었다. 거부감은 계단이 너무 높다는 신호다. 13단계로 넘겨 보는 그림을 본 뒤에는 기대값 6개를 바로 적을 수 있었다.
- **입력 → 출력만 알아도 쌓을 수 있다.** `execute_line`을 한 줄씩 읽는 건 끔찍했지만 그럴 필요가 없었다. 문만 알고 테스트로 확인했으면 그 위에 쌓을 수 있다. 계층화의 이점이다.
- **비유 대신 정확한 용어.** "손님" 대신 **APP**. 개념을 알고 나면 진짜 이름으로 부른다.
- **함수는 타입만이 아니라 뜻까지.** `char *execute_line(hashtable *, const char *)`는 "해시 테이블과 명령 한 줄을 받아 답 한 줄을 돌려준다"까지 말해야 설명이다.
