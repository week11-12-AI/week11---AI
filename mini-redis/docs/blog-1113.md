# 미니 레디스 1일차: 코드 한 줄 없이 큰 그림부터

> 크래프톤 정글 13기 · 11/13
> ✅ = 내가 내 말로 설명한 것 / ❔ = AI 초안, 아직 실행으로 확인 안 함

오늘은 미니 레디스 과제의 첫날이었다. 처음엔 "API 서버? 해시 테이블? TTL?"부터 몰랐다. 그래서 코드를 쓰기 전에 **전체 구조와 흐름을 내 말로 설명할 수 있을 때까지** 이해하는 데 하루를 썼다.

---

## 1. 레디스는 물품보관함이다

- 레디스: 데이터를 **메모리**에 들고 있으면서 요청에 답하는 **서버 프로그램**. 주로 캐시로 쓴다.
- key(보관함 번호)를 대면 value(물건)가 나온다. 하는 일은 넣기(SET), 꺼내기(GET), 버리기(DEL).
- 왜 빠른가: 원본(디스크 DB, 네트워크 너머 API)은 느리고, 메모리는 빠르다. 한 번 가져온 값을 넣어 두고 다시 쓴다.

내가 정리한 것 ✅
- 서버는 실행되면 요청을 기다리다가, 요청이 오면 정해진 약속대로 응답한다.
- 성능 비교에서는 **첫 요청과 반복 요청을 따로** 잰다. 첫 요청은 "원본에 다녀오기 + 보관함에 넣기"라서 오히려 느리다.

## 2. 요청 흐름: 두 갈래 (cache-aside)

레디스는 DB를 모른다. DB에 다녀오는 건 항상 APP(손님)이다. 보관함을 옆(aside)에 두고 손님이 알아서 챙기는 방식이라 cache-aside라고 한다.

내가 그린 흐름 ✅
- i) APP 요청 → 레디스에 해당 데이터 있음 → APP이 데이터 갖고 옴
- ii) APP 요청 → 레디스에 해당 데이터 없음 → APP이 DB에서 해당 데이터 읽고, 레디스에 저장

## 3. 부품 지도

| 부품 | 하는 일 |
|---|---|
| A. 보관함 (해시 테이블) | SET / GET / DEL |
| B. 창구 (API) | 손님 요청을 받는다. 직원 1명 |
| C. 만료·무효화 | 시간이 지나면 / DB가 바뀌면 쪽지를 지운다 |
| D. 다운 대비 | 서버가 꺼져도 데이터를 남긴다 (선택 과제) |
| E. 손님 + 느린 원본 | 레디스 유무별 응답 시간 비교 |

**핵심은 A다.** 과제 원문이 "설명할 수 있어야 한다"고 콕 집은 게 해시 테이블이다.

## 4. A. 해시 테이블과 체이닝

내가 정리한 것 ✅
- 서랍장은 배열이다. 서랍이 N개 있다.
- 해시 함수는 key를 넣으면 몇 번째 서랍인지 계산한다.
- `% N`(나머지)은 아무리 큰 숫자도 0 ~ N-1 서랍 번호 안으로 접어 준다. 시계가 25시를 1시라고 하는 것과 같다.
- 충돌(다른 key가 같은 서랍)은 **막을 수 없다.** 이름은 끝없이 많고 서랍은 N개뿐이니까. 그래서 충돌이 나도 괜찮게 만든다 → **체이닝**: 같은 서랍의 쪽지를 연결 리스트로 잇는다.
- C에서 key, value는 둘 다 주소다. 글자 길이가 제각각이라서.
- GET / SET / DEL은 1. 서랍 고르기(해시 함수) 2. 줄 걷기(next 따라 이름 비교)가 공통이다 → 함수 하나로 만들어 셋이 같이 쓴다.
- SET에 같은 이름이 이미 있으면 값만 바꾼다. 같은 이름 쪽지는 한 장만 있어야 한다.
- DEL에서 맨 앞 쪽지를 지울 때는 서랍의 화살표를 바꾼다.

```
서랍 0: [박지성|010-4] → [김철수|010-1] → [김영희|010-2] → NULL
GET "김영희": 해시 함수 → 0번 서랍 → 김철수? 아님 → next → 김영희? 맞음 → 010-2
```

미룬 것: 줄이 길어지면 느려진다 → 서랍 수를 늘리고 다시 나눠 담는다(리사이즈).

## 5. B. 창구: 직원이 1명이다

내가 정리한 것 ✅
- 해시 테이블을 read/write 하는 스레드는 1개다. 그래서 동기화 문제가 발생하지 않는다. (은행 대기표와 같은 이치)
- 약점은 여러 요청이 왔을 때 순차적으로 처리하기 때문에, 앞의 요청이 해결되어야 뒤의 요청이 해결된다는 것이다. → 그래서 명령 하나하나를 짧게 유지한다.
- 프로세스 간에는 격리되어 있어서 각자의 메모리를 read/write 할 수 없다. 즉, 레디스 서버와 APP은 운영체제를 매개해야 한다.

지난주에 배운 **브라우저 메인 스레드**와 같은 구조다. 직원 1명이라 동시에 안 만지는 대신, 오래 걸리는 일 하나가 모두를 기다리게 한다.

직원 1명이 손님 여럿을 상대하는 방법: 전화기 여러 대 중 **불 켜진 것(요청이 도착한 것)만** 골라서 처리한다. 이 기능을 운영체제가 제공한다 (epoll). ❔

## 6. C. 만료 vs 무효화

내가 정리한 것 ✅
- **만료**는 시간 때문에, 레디스가 알아서 지운다.
- **무효화**는 DB 때문에, APP이 지운다.
- 외우는 고리: 만료 = 유통기한, 무효화 = 리콜.
- 처음에 둘을 정확히 반대로 말했다. 단어 뜻(유통기한 만료 / 리콜)으로 묶으니 바로잡혔다.

무효화 흐름 ✅: DB만 고치고 레디스를 안 건드리면 레디스는 옛 값을 준다 → DB를 고칠 때 DEL로 쪽지를 지운다 → 다음 GET은 "없음" → APP이 DB에서 읽고 레디스에 저장 → 새 데이터를 쓴다.

만료 처리 방법은 "꺼낼 때 확인"과 "가끔 청소" 두 가지다. 이번 과제는 "꺼낼 때 확인"으로 충분하다. "가끔 청소"는 가비지 컬렉터와 닮았다.

## 7. D. 다운 대비

내가 정리한 것 ✅
서버가 꺼지면 메모리의 데이터는 휘발된다. 대비하는 방법은 2가지다.
- **스냅샷**(게임 세이브): 주기적으로 레디스의 모든 데이터를 디스크에 저장한다. 서버가 켜지면 디스크의 해당 데이터를 복원한다. 마지막 세이브 이후의 데이터는 여전히 리스크가 남아 있다.
- **로그**(가계부): 레디스가 수정될 때마다 해당 명령을 디스크에 저장한다. 파일을 처음부터 다시 실행해서 재현할 수 있다. 명령을 하나하나 실행하면서 재현하기에 서버가 다시 켜지면 느리다.

## 8. E. 성능 비교: 기대값부터

내가 정리한 것 ✅
느린 원본을 만들어서, 레디스를 쓸 때와 안 쓸 때의 응답 시간(요청을 보내고 값을 받기까지 걸린 시간)을 측정 비교한다.

기대값 (원본 1초, 레디스 0초, 같은 요청 10번):
- 레디스 없이: 1초 × 10번 = 10초
- 레디스 쓰고: 1초 + 0초 × 9번 = 1초

실제로는 레디스도 0초가 아니다(운영체제를 거쳐 오가니까). 그 차이가 실험에서 배울 곳이다.

## 9. 설계 결정

- **언어: C** ✅ — JS보다 C에 익숙해지고 싶고, 실제 레디스 서버가 C 프로그램이라서. 실행은 WSL Ubuntu.
- **명령 형식**: 한 줄에 명령 하나, 띄어쓰기로 자른다. 0번째 = 명령, 1번째 = key, 2번째 = value ✅ (PintOS argument passing과 같은 원리)
- 값에 띄어쓰기가 있으면 따옴표로 묶는다: `SET 날씨 "맑은 하늘" EX 60` ❔
  - "2번째부터 전부 값"으로 하면 `EX 60`까지 값에 먹혀 버린다. 내 규칙을 다른 경우에 대 보다가 깨지는 걸 찾았다 (레드팀).
- **이상한 입력**: 약속을 어기면 `(error) 이유`로 답하고 보관함은 건드리지 않는다. 서버는 죽지 않는다. ❔ (검토된 기대값, 실행 전)
- 복잡도를 통제하는 요령: 예외는 규칙 하나로 묶고, 검사는 창구에서 전부 해서 보관함에는 깨끗한 입력만 들어가게 한다.

## 10. 오늘 배운 일하는 방법

- **기대값 → 실행 → 비교 → 고치기.** 공부든 일이든 같은 뼈대다. 아예 모를 땐 먼저 실행해서 감을 잡는다.
- **백지 테스트**: 안 보고 그려 보면 빠진 곳이 곧 덜 잡힌 곳이다. 오늘은 부품 이름(A = 해시 테이블, B = 창구)과 흐름 속 기한 확인 위치가 빠졌다.
- **"다른 답이면 무엇이 깨지나?"** 정답 옆에 틀린 답을 일부러 놓고 왜 안 되는지 따지면 규칙이 선명해진다. 지난주의 레드팀과 같다.
- **AI의 단정을 원문으로 따지기**: AI가 "기준은 하나뿐", "과제 문장이 이미 cache-aside"라고 했는데, 원문 근거를 물으니 둘 다 과장이었다.
- **기초 vs 응용**: 내가 설명할 것(해시 테이블, 직원 1명, 만료·무효화, 다운 대비)과, AI에게 맡기고 동작으로 검증할 것(소켓, epoll, 명령 자르기)을 나눴다.
- **큰 그림과 이유는 항상 내가 쥔다.** 세부로 들어가기 전에 지금 위치와 왜를 먼저 확인한다.
