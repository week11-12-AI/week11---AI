## 1. 계단 3: 터미널 두 개로 서버와 APP을 직접 붙여 봤다

터미널 A에서 서버를 켜고, 터미널 B에서 `nc 127.0.0.1 6379`로 APP 역할을 했다. nc(netcat)는 소켓에 연결해서 내가 친 글자를 보내고 받은 글자를 보여 주는 도구다. 진짜 APP을 만들기 전까지 대신 쓰는 가짜 APP이다.

### 서버가 시작할 때 OS에 부탁하는 4단계

```
socket  입구 만들기 → bind  번호(6379) 붙이기 → listen  받을 준비 → accept  하나 받기 (잠듦)
```
- 순서와 역할만 알면 된다. 인자를 어떻게 채우는지는 AI에 맡기고 동작으로 검증할 응용이다.
- 다음 주 DBMS Phase 3(API 서버)에서 그대로 다시 쓴다.

### 직접 확인한 것 ✅

- 서버를 켜면 `[① 연결 기다림]`에서 멈춘다. 멈춘 게 아니라 **accept 안에서 잠든 것**이다. PintOS의 `sema_down`처럼 BLOCKED 상태다.
- nc가 연결하자 `[연결됨] fd = 4`가 찍혔다. 0·1·2는 표준 입력·출력·에러, 3은 listen 입구라서 4다.
- APP 1: `SET 날씨 맑음` → OK, `GET 날씨` → 맑음. **B에서 Ctrl+C로 끊자 A에 `[연결 닫음]` → `[① 연결 기다림]`이 찍혔다.**
- APP 2: fd가 다시 4였다. 내 말로 ✅: **"반납했으니 또 받을 수 있나 보군."** OS는 비어 있는 번호 중 가장 작은 것을 준다.
- APP 2에서 `GET 날씨` → 맑음. **APP 1이 끊어도 데이터는 서버 메모리에 남는다.** (토요일에 나는 nil이라고 틀렸었다.)
- 서버 재시작 → `GET 날씨` → (nil). **휘발** 확인.

### 서버 루프 두 겹과 탈출 조건

```
main()  바깥 루프 (서버가 꺼질 때까지)
│  ① accept: APP 연결 기다리기 (잠듦)
│  serve()  안쪽 루프 (그 APP이 연결된 동안)
│  │  ② read: 한 줄 읽기 (잠듦)  ── 0글자면 탈출
│  │  ③ execute_line
│  │  ④ write: 답 보내기
│  └  ⑤ ②로
└  close(fd) → ①로
```

내 말로 ✅: **main() 안에 바깥 루프, serve() 안에 안쪽 루프. main이 연결 하나를 받을 때마다 serve를 부르고, serve가 return하면 close(fd)가 실행된다.**

틀렸다가 고친 것
- "read가 0"을 `read(0)`으로 읽었다 ❌. 0은 **넣는 값이 아니라 돌려받는 값(읽은 글자 수)**이다. 연결이 끊기면 더 올 글자가 없으니 0이다. PintOS에서 파일 끝을 read하면 0이 나오는 것과 같다.
- APP이 오래 아무것도 안 보내면 "read가 호출 안 된다" ❌ → **read는 이미 호출됐고 안에서 잠들어 있다.**
- `[① 연결 기다림]` 뒤에 잠든 함수가 listen ❌ → **accept.** listen은 "받을 준비"를 등록만 하고 바로 돌아온다. **서버가 잠드는 곳은 accept(연결 기다림)와 read(글자 기다림) 두 군데뿐이다.**

### 기대와 다른 결과 1: 이상한 바이트

`GET 날씨`를 쳤는데 `(error) 모르는 명령`이 왔다. 서버가 받은 줄은 `�GET 날씨`였다. GET 앞에 깨진 바이트가 붙어 있었다. 한글을 쳤다 지울 때 바이트 조각이 남은 것으로 보인다 ❔. 다시 치니 `(nil)`이 나와서 **서버는 정상이고 입력 쪽 문제**였다. 덤으로 확인한 것: **이상한 입력에도 서버는 `(error)`로 답하고 죽지 않았다.**

### 기대값이 아무것도 증명하지 못하는 테스트

원래 계획은 "서버 재시작 → GET → nil"이었다. 그런데 직전에 이미 DEL을 해서 nil인 상태였다. 이대로면 **휘발돼서 nil인지 원래 없어서 nil인지 구분이 안 된다.** 그래서 재시작 직전에 SET을 하고, GET으로 `맑음`을 확인한 뒤 재시작했다. 테스트는 **결과가 갈릴 수 있게** 짜야 의미가 있다.

## 2. 깊은 복사, 드디어 끝

계단 1부터 반쯤만 이해한 상태(❔)였다.

- `ht_set`이 받는 `"맑음"`은 execute_line이 잠깐 쓰는 메모장(buf) 안에 있다. 이 메모장은 **명령 하나가 끝나면 free된다.**
- 얕은 복사(주소만 저장)를 하면 해시 테이블 값이 **댕글링 포인터**가 된다 ✅ (내가 먼저 말함).

실험 ✅: `hashtable.c`를 얕은 복사로 바꾸고 nc로 확인했다.

| | 내 기대 | 실제 |
|---|---|---|
| SET | OK | OK |
| GET | 예측 불가 (UAF라서 undefined behavior) | 답 없음, nc 종료 |
| 서버 | 에러, 댕글링 포인터 | **AddressSanitizer: heap-use-after-free ... in strlen** → 서버 죽음 |

- ASan이 없으면 내 말대로 예측 불가다. **ASan은 버려진 메모리를 처음 건드리는 순간 멈춰서 매번 확실히 터지게 만든다.** 이게 가드레일을 켠 이유다.
- `in strlen`: GET의 답을 복사하려고 글자 수를 세다가(strlen) 버려진 메모리를 읽은 순간 걸렸다.

내 말로 ✅: **"읽은 데이터를 해시 테이블에 깊은 복사하지 않고 얕은 복사를 하면, (execute_line의 메모장을) 버렸을 때 해시 테이블의 값은 댕글링 포인터가 된다."** 해시 테이블은 DEL 전까지 오래 들고 있어야 하는데, 넘겨받은 글자는 명령 하나가 끝나면 사라진다.

## 3. 계단 4: 만료

과제 원문: "보관 기간이 만료된 값을 요청받았을 때, 이를 어떻게 처리할지."

- `SET 날씨 맑음 EX 60` → 노드에 `expire_at`(만료 시각) = 지금 + 60초
- TTL(Time To Live) = **기간**(60초), expire_at = **시각**. expire_at이 0이면 "만료 없음"이라는 약속된 표시다.
- 확인 위치 ✅: **(나) 노드를 찾은 뒤, 값을 돌려주기 전.** 만료 시각이 노드에 적혀 있으니 찾기 전에는 알 수 없다. 이 방식이 **lazy expiration**이다. 약점: 아무도 찾지 않는 만료된 노드는 메모리에 남는다.

내 기대값 7개 ✅: EX 2 → OK / 바로 GET → 맑음 / 3초 뒤 → nil / 만료된 key DEL → 0 / `EX abc`, `EX -5`, `EX`(숫자 없음) → error

내 지적 ✅: "SET은 만료 확인 안 해도 되지 않나? 그냥 덮어쓰면 되니까." → **맞다. 결과가 같다.** 코드는 "만료된 건 없는 것"이라는 규칙 하나를 GET/SET/DEL에 똑같이 적용하려고 셋 다 확인한다.

테스트는 3초를 실제로 기다리지 않는다. **가짜 시계**로 시간을 흘린다. 진짜 시계로는 nc에서 `EX 5`를 걸고 확인했다 ✅. 첫 시도에서 GET이 바로 nil이 나왔는데, 내가 타이핑을 5초 넘게 해서였다.

만료된 GET을 내 말로 ✅
1. 해시 함수로 날씨가 들어 있는 리스트를 찾는다
2. 그 리스트에서 key가 날씨인 노드를 찾는다
3. 그 노드의 expire_at과 지금 시각을 비교한다
4. 지났으니까 그 노드를 체인에서 빼고 메모리를 반납한다 (DEL과 같은 동작)
5. APP에게 (nil)이라고 답한다

처음엔 1번을 "해시 함수로 **GET**을 고른다"고 썼다 ❌. GET은 2층(command)에서 어떤 함수를 부를지 고르는 데 쓰고 끝난다. **해시 함수의 입력은 key다.** 14일 아침 복습에서도 약했던 곳이다.

## 4. 구멍 발견: 해시 테이블 구조체

"entry가 bucket이야?"라는 질문이 나왔다. 해시 함수, entry, hashtable 구조체가 다 흐렸다. 머리가 학습을 거부했다. 원인은 두 가지였다.
- **연결 리스트**가 단단하지 않았다.
- 비유(서랍·쪽지)에서 정확한 용어(bucket·entry)로 바꾸면서 13일에 이해한 것과 **연결이 끊겼다.**

15분 쉬고 한 층씩 다시 쌓았다.

내 말로 ✅: **"연결 리스트(노드 여러 개가 엮인 체인)가 n개 있고, 각 연결 리스트의 첫 노드 주소를 배열에 담는다."**

```
buckets[0] = NULL
buckets[1] ──▶ [날씨 | 맑음] ──▶ NULL
buckets[2] = NULL
buckets[3] ──▶ [이름 | 진훈] ──▶ [나이 | 30] ──▶ NULL     (충돌 → 체인)
```

| PintOS | 우리 코드 |
|---|---|
| `struct list_elem` (노드) | `entry` (key, value, expire_at, next) |
| `struct list` (리스트 하나의 머리) | `buckets[i]` 하나 |
| (없음) | `hashtable` = 머리 n개를 담은 배열 + 개수 n |

- bucket = 칸(서랍), entry = 데이터 한 건(쪽지). buckets는 칸 여러 개라는 뜻이다. entry가 여러 개라서 붙은 이름이 아니다.

해시 함수 (안 보고) ✅
- 입력: key
- 출력: 배열 칸 번호 (0부터 n-1까지)
- 이유: 모든 연결 리스트를 탐색하지 않고, 곧장 정확한 연결 리스트로 가기 위해서

**"같은 key는 항상 같은 번호"**는 숫자 예시로는 납득이 안 됐다. **도서관 책장**으로 납득했다 ✅.
- 규칙: "책 제목의 첫 글자로 책장을 정한다." ㄱ → 1번 책장
- "강아지"를 꽂을 때도 ㄱ → 1번, 일주일 뒤 찾을 때도 ㄱ → 1번
- **규칙이 제목만 보니까** 같은 답이 나온다. ㄱ으로 시작하는 책이 여러 권이면 1번 책장에 같이 꽂힌다 = 충돌
- 이 약속이 깨지면 SET은 1번에 넣고 GET은 3번을 뒤져서, 있는데도 못 찾는다.

## 5. 계단 5: 성능 비교

과제 원문: "간단한 API를 만들고 응답 값을 미니 레디스에 저장하여 활용" + "레디스를 쓸 때와 안 쓸 때의 성능 차이 비교"

프로세스 3개라서 터미널도 3개다. **서버는 안 끝나는 프로그램이라 터미널 하나를 차지한다** ✅.
```
A: 레디스 서버 (6379)
B: 느린 API 서버 (8000)  답하기 전에 1초 쉼. 가짜 원본 (느린 DB나 외부 API 흉내)
C: APP (bench)           같은 요청 10번, 레디스 없이 vs 레디스 쓰고
```
느린 API 서버도 서버라서 루프 구조가 같다. ③만 "execute_line" 대신 "1초 쉬고 답 만들기"다.

레디스 쓰는 쪽은 13일에 그린 **cache-aside** 그대로다. GET → 있으면(hit) 그 값, 없으면(miss) 느린 API → 레디스에 SET → 그 값. hit/miss는 CPU 캐시와 같은 개념이다 ✅.

내 기대 ✅: 느린 API는 **1번** 호출된다. 최초에 한 번은 원본에서 읽어 레디스에 저장해야 하니까. 시간은 13일 기대값 그대로 10초 vs 1초.

### 발견 1: "직원 1명"의 약점을 실제로 밟았다

bench가 멈췄다. nc가 레디스에 연결된 채로 있었는데, 서버 스레드가 1개라 **nc 연결의 read에 붙잡혀서 bench 연결을 accept하지 못했다.** 지금 서버는 연결 하나를 끊길 때까지 붙잡는다. 진짜 레디스는 epoll로 해결한다. 과제 범위 밖이라 한계로 남겼다.

### 발견 2: 기대 1,000 ms, 실제 1,437 ms

| | 기대 | 첫 측정 | 고친 뒤 |
|---|---|---|---|
| 레디스 없이 | 약 10,000 ms | 10,011 ms | 10,011 ms (그대로) |
| 레디스 쓰고 | 약 1,000 ms | **1,437 ms** | **약 1,009 ms** |
| hit 1번 | 거의 0 | **약 44 ms (10번 다 똑같이)** | **약 0.6 ms** |

hit이 전부 44 ms로 똑같았다. 해시 테이블에서 찾는 일은 그보다 훨씬 빠르니 **어딘가에서 기다리는 시간**이다. 서버가 답을 **두 번에 나눠**(`맑음`, `\r\n`) 보내서 OS가 매번 약 40 ms씩 기다렸다. 한 번에 보내게 고치니 0.6 ms가 됐다 ✅ (직접 재서 확인). 느린 API는 원래 한 번에 보내서 이 문제가 없었다는 게 단서였다.

- "OS끼리 무엇을 왜 기다렸나(Nagle 알고리즘, delayed ACK)"는 **응용**으로 분류했다. 내가 설명할 기초는 "나눠 보내니 40 ms 늦었고, 한 번에 보내니 0.6 ms" 한 문장이다.
- 13일 블로그에 쓴 문장 "실제로는 레디스도 0초가 아니다. 그 차이가 실험에서 배울 곳이다"가 정말로 그랬다.

결론 내 말로 ✅: 둘 다 최초에는 원본(DB)에서 읽어 와야 한다. 레디스가 없으면 나머지 9번도 똑같이 원본에 다녀오고, 레디스가 있으면 나머지 9번은 레디스 서버에 소켓으로 물어 0.6 ms 만에 받는다. 원본 1,000 ms vs 레디스 0.6 ms.

## 7. 오늘 배운 일하는 방법

- **처음 보는 개념은 "보기 → 따라 말하기 → 기대값".** 탈출 조건을 몰랐던 건 내 탓이 아니라 그림에 그 장면이 없어서였다. 장면을 추가하고 실행에서 `[연결 닫음]`을 직접 보니 바로 잡혔다.
- **머리가 거부하는 건 과부하 신호다.** 하루에 소켓, accept, read, 댕글링 포인터, 만료, 구조체가 다 나왔다. 15분 쉬고 한 층씩 다시 쌓으니 "해시 함수 개념 이해 못 했네"가 두 시간 뒤 "안 보고 설명"이 됐다.
- **비유와 정확한 용어는 짝으로.** 정확한 용어만 쓰면 이해했던 것과 연결이 끊긴다. 당분간 "bucket(서랍)", "entry(쪽지)"처럼 같이 쓴다.
- **"무지성으로 패스"를 알아챘다.** `make test`가 두 줄을 찍는데 각각이 무엇인지 몰랐다 → Makefile 5~7줄을 보고 확인했다. AI가 쓴 **연결용 파일**(Makefile 같은 것)은 검토에서 빠지기 쉽다.
- **기초와 응용을 나눈다.** Nagle 알고리즘은 응용이다. 내가 다 이해하지 못해도 되고, 동작(44 → 0.6 ms)으로 검증했으면 충분하다.
- **테스트는 결과가 갈릴 수 있게.** 이미 nil인 상태에서 재시작 후 nil을 기대하는 건 아무것도 증명하지 못한다.
- **기대와 다르면 누구 탓인지 가른다.** `�GET`은 서버가 아니라 입력 탓이었다. 다시 쳐서 갈랐다.

## 8. 곁가지: ChatGPT는 왜 무료일까? (킹스맨의 공짜 휴대폰?)

영화 킹스맨의 악당은 휴대폰과 통신을 공짜로 뿌린다. AI 무료 서비스도 같은 원리일까? 궁금해서 세 갈래로 자료를 찾았다. 아래는 **회사 공식 문서, 미국 공정거래위원회(FTC) 보고서, 여러 언론이 같은 내용으로 보도한 것**만 남긴 것이다. 보도 하나에만 나온 숫자는 뺐다. (2026년 11월 기준)

### 데이터 수집과 모델 학습

- ChatGPT 개인 요금제(무료 포함)는 **기본값이 "대화를 학습에 사용"**이다. 사용자가 설정 > 데이터 제어에서 직접 꺼야 하고, 끄면 그 뒤 대화부터 적용된다. (OpenAI 도움말)
- 학습을 꺼도 **👍/👎 피드백을 누르면 그 대화가 학습에 쓰일 수 있다.** (OpenAI 도움말)
- 기업용 요금제와 API는 **기본적으로 학습에서 제외**된다. (OpenAI 도움말)
- Anthropic(Claude)도 2025년 8월 일반 사용자 약관을 바꿨다. 학습 사용에 동의하면 **보관 기간이 30일에서 5년**으로 늘어난다. 기업용과 API는 해당하지 않는다. (Anthropic 공지)
- ChatGPT 광고: 2026년 1월 발표, 2월부터 **무료 요금제와 Go 요금제**에서 테스트를 시작했다. 대화 맥락을 일부 반영해 광고를 고른다. OpenAI는 광고주에게 대화를 넘기지 않는다고 밝혔다. (Axios, NBC News)
- 2026년 2월 OpenAI 발표: 주간 사용자 9억 명, 유료 구독자 5천만 명. 단순 계산하면 **약 5.6%가 돈을 낸다.** (TechCrunch)

### 생태계 락인(Lock-in)과 표준 선점

- 2026년 3월 Claude와 Gemini가 **ChatGPT 메모리를 가져오는 기능**을 내놨다. 다만 메모리 요약을 한 번 복사하는 방식이고, 계속 동기화되지는 않는다. (Tom's Guide, TechRadar 직접 사용 리뷰)
- AI가 외부 도구에 연결하는 규약 **MCP**는 Anthropic이 만들었다. 2025년 12월 **리눅스 재단 산하 중립 기구(Agentic AI Foundation)에 기증**했고, OpenAI, Google, Microsoft, AWS가 참여한다. (리눅스 재단 발표)

### 클라우드 및 인프라 락인

- FTC는 2025년 1월 Microsoft–OpenAI, Amazon–Anthropic, Google–Anthropic 제휴를 조사한 보고서를 냈다. (FTC 보고서)
  - 투자금의 큰 부분을 **투자한 회사의 클라우드에 다시 쓰겠다는 약정**이 있었다.
  - 여러 제휴에 **다른 회사와 일하는 것을 제한하는 조건**이 있었다.
  - 특수 칩과 클라우드 사이를 옮기는 데 오래 걸려서 **갈아타기 비용**이 커질 수 있다.
- OpenAI는 2025년 11월 AWS와 **380억 달러** 규모의 클라우드 계약을 맺었다. (여러 언론)
- Microsoft의 OpenAI 모델 **독점 라이선스는 2026년 4월 계약 수정으로 끝났다.** (TechCrunch 외 여러 언론)
- Anthropic은 2025년 10월 Google TPU를 **최대 100만 개**까지 쓰는 계약을 발표했다. Amazon은 Anthropic에 80억 달러를 투자했고, Amazon이 주 학습 파트너로 남았다. (여러 언론)

### 사실에서 읽히는 것

- **"공짜 뒤에 다른 대가가 있다"**는 자료로 확인된다: 학습 기본값이 켜져 있고, 대화 맥락으로 광고를 고르고, 돈을 내는 사람은 약 5.6%다. 반대로 돈을 내는 기업 고객은 기본적으로 학습에서 빠진다.
- 킹스맨처럼 **숨겨 둔 조종 장치**가 있다는 자료는 찾지 못했다.
- 사용자 쪽 락인은 메모리 가져오기와 MCP 중립화로 **약해지는 흐름**이 보인다. 반면 AI 회사들은 수백억 달러 약정으로 **클라우드 회사에 묶여 가고 있다.**
