## 2. 처음 보는 시스템을 파악한 순서

처음엔 README를 읽고 흐름 그림을 봤는데 하나도 머리에 남지 않았다. 순서를 바꿨다.

> **눈에 보이는 화면 → 그 뒤의 흐름 → 코드**

1. **직접 띄웠다** ✅: 팀 브랜치를 `git worktree`로 옆 폴더에 펼치고, 터미널 두 개로 서버를 켰다.
   - 터미널 A: `python3 -m mini_redis.server` → 4175번 포트 (Redis)
   - 터미널 B: `python3 server.py` → 4173번 포트 (앱 서버 = 화면 + API + DBMS)
2. **직접 써 봤다** ✅: 퍼즐을 21번 만에 풀고 기록을 저장했다. 랭킹 1위에 내 이름이 올라갔다.
3. **실험으로 목격했다** ✅
   - Redis 계기판(`/api/cache/stats`)을 열어 두고 랭킹을 두 번 새로고침했다. 내 예상은 "적중 2번"이었는데 실제로는 **미스 1 + 적중 1**이었다. 이유: 계기판에 `keys: 0, expired: 3`이 있었다. 30초 TTL이 지나서 캐시가 비어 있었던 것이다. **TTL을 숫자로 목격했다.**
   - Redis 서버를 꺼 봤다. 계기판은 연결 거부, 그런데 **랭킹은 그대로 보였다.** 원본은 DB에 있고 Redis는 보조라는 걸 눈으로 봤다.

포트 개념도 이렇게 붙었다. 터미널 하나 = 프로그램 하나 = 포트 하나. 127.0.0.1은 "이 컴퓨터", 포트는 그 안의 창구 번호다.

## 3. 오늘 붙잡은 문장들

### 앱 서버는 처음엔 미스인지 모른다 ✅
내 예상: "미스면 DB만 가니까 HTTP는 0번". 틀렸다. 냉장고(Redis)를 **열어 봐야** 반찬이 없다는 걸 안다.

```
① 브라우저 → 앱 서버   "랭킹 보여 줘"          HTTP
② 앱 서버  → Redis     "랭킹 있어?" → "없어"    HTTP   ← 이걸로 미스를 알게 됨
   앱 서버  → DB        TOP 10 뽑기             HTTP 아님 (같은 프로그램 안)
③ 앱 서버  → Redis     "30초 맡아 줘"           HTTP
```
미스 = HTTP 3번, 적중 = HTTP 2번. 팀 코드(`api.py`의 `ranking` 함수, 26~36줄)를 원본 그대로 보고 확인했다.

### 캐시인데 왜 더 느렸나 ✅
팀 README의 성능 표가 정직했다.

| 조건 | 평균 응답 | DB 조회 |
|---|---|---|
| 캐시 없이 | 8.6 ms | 100번 |
| 캐시 적중 | 26.2 ms | **0번** |

- DBMS는 앱 서버 **안**에 있어서 HTTP 없이 함수로 부른다.
- Redis는 **따로 떨어진 프로그램**이라 HTTP를 한 번 더 거쳐야 하고, 그만큼 시간이 든다.
- 그래서 이 규모에서 캐시가 줄인 건 속도가 아니라 **DB 조회 횟수(100 → 0)**다.

처음엔 "Redis에 가려면 무조건 HTTP니까 캐시는 쓸모없는 구조 아닌가?"라고 의심했다. 과제 원문을 다시 보니 답이 있었다. "**외부에서 사용할 수 있는 API 형태**로 만들고, Redis 사용/미사용 **성능을 비교**하라." 그래서 별도 서버 + HTTP 구조가 된 것이다.

> **캐시는 아끼는 일이 통신보다 비쌀 때 이득이다.** 랭킹은 DBMS가 전체 기록을 정렬해 상위 10개를 뽑는 일이다. 기록이 충분히 많아지고 이용자가 많아지면 이 일이 무거워지고, 그때 Redis가 의미를 가질 수 있다. (❔ 팀이 측정하진 않았다)

"TOP 10을 계산한다"는 말이 와닿지 않는다고 파고들어서 나온 문장이다. 뭉뚱그린 말 뒤에 이유가 숨어 있었다.

### 기록과 랭킹은 다르다 ✅
- **기록** = 한 사람이 한 번 푼 결과 한 줄(`진훈 / 21회 / 39.3초`). DB에 있는 **원본**.
- **랭킹** = 기록을 정렬해 뽑은 TOP 10 표. Redis에 30초 있는 **사본**. 키 하나에 표 전체가 들어간다.

> 새 기록은 DB에만 저장되고, 앱 서버가 Redis의 기존 랭킹을 지운다. 다음 조회 때 **미스**가 나서 새 기록이 반영된 새 랭킹이 만들어진다.

처음엔 "다음 **적중** 때 새 랭킹이 만들어진다"고 말했다. 새 랭킹은 언제나 **미스** 때 만들어진다. 적중은 꺼내기만 한다.

### DBMS: 파일은 원본, B+ 트리는 목차 ✅
기록 하나가 저장되면 ① 변경 기록 파일 끝에 한 줄 추가 + fsync, ② 그다음에만 메모리 B+ 트리에 id → 파일 위치. 서버를 켜면 파일을 처음부터 다시 읽어 트리를 복원한다. 나는 처음에 "메모리의 기존 레코드는 삭제된다"고 답했는데, 지워지는 건 **Redis 캐시**였다. DBMS 메모리는 지우지 않고 적는다.

### 증거로 확인한 것들 ✅
- "팀원은 B+ 트리를 구현 안 했다"고 기억하고 있었다 → 팀 코드에 `bplus_tree.py`(154줄)가 있고 README에 "직접 구현"이라고 적혀 있다. 기억이 틀렸다.
- "랭킹 1위만 캐시에 저장하나? DELETE 한 번으로 충분한가?" → `cache.set(key, result, 30)`의 result가 **TOP 10 전체**라 지우기 한 번이면 충분하다.
- "같은 사람이 같은 기록을 또 내면?" → `outcome="kept"`로 기존 유지, 캐시도 안 지운다.
