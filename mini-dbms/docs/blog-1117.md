## 1. 아침: 큰 그림이 "전혀" 기억나지 않았다

어젯밤 그린 DBMS 큰 그림을 안 보고 다시 그려 보려 했는데, 하나도 떠오르지 않았다. 그래서 이미 손에 붙은 **레디스 3층**에 짝지어 다시 봤다.

| 층의 일 | 레디스 (만든 것) | DBMS (만들 것) |
|---|---|---|
| 입구 (네트워크) | server.c | API 서버 + 워커 스레드 n개 (Phase 3) |
| 명령 처리 | command.c (`execute_line`) | 파서 → 실행기 (Phase 1) |
| 데이터 보관 | hashtable.c (메모리) | 테이블 파일 (디스크) + B+ 트리 (메모리) (Phase 1, 2) |

부품마다 **"이게 없으면 뭐가 안 되나"**를 붙이니 이름만 외울 때보다 덜 휘발됐다. ✅

| 부품 | 하는 일 | 없으면? |
|---|---|---|
| CLI | SQL 파일을 읽어 DB 엔진에 넘긴다 | SQL 파일을 넣을 곳이 없다 |
| 파서 | SQL 한 줄을 자르고 이름표를 붙인다 | 실행기가 글자 덩어리만 받아 무엇을 할지 모른다 |
| 실행기 | 이름표를 보고 테이블 파일·B+ 트리에 일을 시킨다 | 파서 결과가 실행되지 않는다 |
| 테이블 파일 | 레코드 원본을 보관한다 (디스크) | 꺼지면 데이터가 휘발된다 |
| B+ 트리 | id로 레코드의 파일 속 위치를 알아낸다 (메모리) | 모든 데이터를 전수조사해야 한다 |
| API 서버 | 소켓으로 외부 요청을 받는다 | 다른 프로그램이 DB를 쓸 수 없다 |
| 워커 스레드 n개 | 요청 여러 개를 동시에 처리한다 | 한 요청이 끝날 때까지 나머지가 기다린다 |

## 2. "요구사항을 완전히 이해한 다음 구현해야 하지 않나?"

이 찜찜함은 **이해를 두 종류로 나누니** 풀렸다.

| | 무엇·왜 (요구사항) | 어떻게 (구현) |
|---|---|---|
| 질문 | 무엇을 만들고, 왜 필요하고, 다 됐는지 어떻게 아나? | B+ 트리 노드는 어떻게 쪼개지나? |
| 언제 | **구현 전에** | **만들면서** |

레디스도 깊은 복사가 왜 필요한지는 얕은 복사로 바꿔 ASan 에러를 본 뒤에야 납득됐다. 구현 전 끝 조건은 "완전한 이해"가 아니라 **"무엇·왜·끝 조건을 말할 수 있다"**다. ✅

## 3. 진도: 2시간 45분 늦었다

11시까지 끝낼 "큰 그림 + 언어 결정"이 13:46에 끝났다. 언어는 **C** (레디스 server.c 재사용, pthread가 PintOS와 같은 모양).

과제 원문에 근거가 있었다: *"AI가 전체 코드를 생성해도 된다. 다만 핵심 로직은 이해하고 설명할 수 있어야 한다."* 그래서 방식을 바꿨다.
- AI가 Phase 단위로 짜고, 나는 **핵심 로직만** 읽는다
- "죽도 밥도 안 될까" 걱정에 안전장치 3개: ① 핵심 로직을 미리 정한다 ② 기대값 → 실행 → 비교는 그대로 ③ **핵심 로직을 내 말로 설명 못 하면 다음 Phase로 안 간다**

핵심 로직 3개는 과제 원문 60줄 "입력(SQL) → **파싱** → **실행** → **저장**"에서 뽑았다: A 파서, B INSERT, C SELECT.

## 4. Phase 1: SQL 처리기

### 처음 보는 프로젝트를 파악하는 법 (외우지 않는다)
1. **폴더 = 종류**: `src` 부품 / `tests` 확인용 / `docs` 기록 / `build` make가 만든 결과물 (커밋 안 함)
2. **입구부터 따라가기**: `cli.c main` → `db_execute` → 파서 → 실행기 → 테이블 파일. 이 한 줄이 큰 그림이다
3. **파일 맨 위 주석**에 역할이 있다

### 헷갈렸던 말들 ✅
- **DB는 데이터, DBMS는 프로그램.** "DB를 실행한다"는 틀린 말이다. 정확히는 "**DBMS(`./build/dbms`)에 SQL 파일을 넣어 실행한다**". 엑셀 파일과 엑셀 프로그램의 관계다.
- **SQL 파일**(queries.sql = 명령)과 **테이블 파일**(data/users.csv = 데이터)은 다르다.
- **CSV** = 한 줄이 레코드, 쉼표가 칸 구분. 그래서 이름에 쉼표를 막았다. 줄 길이가 제각각이라 "5번째 줄"로 바로 못 간다.
- 스키마(`id, name, age`)는 파일이 아니라 **코드 안**에 있다. 그래서 파일엔 머리줄이 없다.

### 기대값 vs 실제
queries.sql을 두 번 실행한 뒤 `cat data/users.csv`:

| | 내 기대 | 실제 |
|---|---|---|
| 첫 줄 | `id name age` 머리줄 | 없음 |
| 레코드 | `1 kim 31` (띄어쓰기) | `1,kim,31` (쉼표) |
| 두 번째 실행 | 4, 5, 6이 끝에 붙음 | ✅ 4, 5, 6이 끝에 붙음 |

두 번째 실행이 1이 아니라 4부터 시작한 이유: **켤 때 테이블 파일을 처음부터 끝까지 읽어 가장 큰 id를 찾고 +1** 한다. 메모리는 꺼지면 사라져도 파일은 남아 있으니까. 그리고 내가 먼저 짚었다: "그러면 켤 때 100만 건이면 시간이 꽤 걸리겠네." ✅ (Phase 2에서 1.1초로 확인)

### 요구사항을 증거로 검증하기
"빠진 게 있나?"라는 질문에 처음엔 "모르겠음"이었다. 방법을 바꿨다. **요구사항 한 줄마다 내가 직접 목격한 증거를 짝짓는다. 짝이 없으면 빠진 것이다.** 목격하지 않은 건 O를 주지 않았다. 증거를 보고 전부 O.

### 내가 만든 실험 (my.sql)
AI가 낸 문제만 맞히지 않고 SQL을 직접 써서 넣었다.

| SQL | 내 예상 | 실제 |
|---|---|---|
| `INSERT INTO users VALUES ('choi', 29);` | OK | ✅ `INSERT 1 (id = 7)` |
| `SELECT * FROM users WHERE age = 28;` | 에러 | ❌ `(0 rows)` |
| `INSERT INTO kor VALUES ('choi', 29);` | 에러 | ✅ `(error) 없는 테이블: kor` |

여기서 오늘의 명제가 나왔다.

> **파서는 모양만 보고, 실행기는 뜻을 본다.** ✅

- `INSERT INTO kor …`는 **모양**이 완벽해서 파서를 통과하고, 실행기가 스키마에서 `kor`를 못 찾아 에러를 낸다.
- `WHERE age = 28`은 모양 ✅ → age 열 있음 ✅ → 파일을 끝까지 읽었는데 28살이 없음 → `(0 rows)`.
- **sql_stmt** = 파서가 모양 검증을 통과시킨 뒤 만든 결과물 = 파서가 실행기에게 건네는 쪽지.

### 파서 세 문장
1. 첫 단어를 보고 INSERT / SELECT 갈래를 고른다
2. 문법 순서대로 조각을 확인하며, 필요한 조각은 sql_stmt 칸에 이름표 붙여 복사한다
3. 순서가 어긋나는 곳에서 바로 에러를 낸다

## 5. Phase 2: B+ 트리 인덱스

### 기초부터 확인했다 (내가 먼저 답함) ✅
1. **반씩 버리며 찾기**: 1~100만 업다운 게임은 가운데를 부르면 최대 **20번**. 2^10 ≈ 1000이니 2^20 ≈ 100만.
2. **시간 복잡도**: 처음부터 하나씩 = O(n) = 100만 번 / 반씩 버리기 = O(log n) = 20번.
3. **파일 속 위치**: `1,kim,31\n`이 9바이트, `2,lee,25\n`가 9바이트이니 `3,park,31`은 **18번 바이트**에서 시작. `tail -c +19 data/users.csv`로 직접 확인.

B+ 트리는 목차다. 레코드 `7,choi,29`가 56번 바이트에 있으면 트리에 **"7 → 56"**을 적어 둔다. `WHERE id = 7`이 오면 목차에서 56을 찾고, 56번 바이트로 바로 가서 한 줄만 읽는다.

### 100만 건 결과 (기대값을 먼저 적고 실행)

| | 내 기대 | 실제 |
|---|---|---|
| 넣기 100만 건 (Phase 1 처리기로) | - | 2.5초 |
| 켜기 (인덱스 재구축) | 101초 | **1.13초** |
| `WHERE id = 500000` (B+ 트리) | 눈 깜짝 | **0.545 ms** ✅ |
| `WHERE name = 'user500000'` (선형) | 50초 | **1.04초** |

- **같은 100만 건에서 name 검색이 id 검색보다 약 1900배 느리다.**
- 켜기와 선형 검색이 비슷한 이유: 둘 다 파일을 처음부터 끝까지 한 번 읽는다. ✅
- 내 감은 50배쯤 크게 잡혀 있었다. 컴퓨터는 파일 100만 줄을 1초 안에 읽는다.
- 트리 높이는 4. 노드 하나가 반이 아니라 수십 갈래로 나눠서, 20번보다 훨씬 적게 내려간다. ❔ (내일 그림으로)

### 넣기가 켜기보다 2.5배 느린 이유
| 켜기 (한 레코드당) | 넣기 (한 레코드당) |
|---|---|
| 파일에서 한 줄 읽기 | SQL 글자 만들기 → 파싱 → 뜻 확인 → id 붙이기 → 파일 끝에 쓰기 |
| 목차에 id → 위치 적기 | 목차에 id → 위치 적기 → 결과 글자 만들기 |

### 구현 중 고친 것 (발표 거리)
처음엔 2만 건 넣기에 **17초**가 걸렸다. INSERT마다 파일 버퍼를 디스크 쪽으로 내보내고 있었다. 모아서 내보내도록 바꾸니 **0.2초**. 레디스에서 응답을 한 번에 써서 44ms → 0.6ms가 된 것과 같은 종류다. 이름은 **버퍼링 / 배칭**. 왜 빨라지는지는 아직 내 말로 못 한다. ❔

## 6. 학습법 점검: 나는 AI를 지렛대로 쓰고 있었나

오후에 스스로 물었다: 대화를 잘 하고 있나, 배우는 법을 배우고 있나, AI를 지렛대로 쓰나, 내 머리를 키우고 있나. 정직한 답은 **"받아쓰기"**였다. 핵심 문장 A·B·C를 전부 AI가 쓰고 나는 확인만 했다. 그러면 머리가 아니라 AI 문장을 알아보는 능력만 커진다.

그래서 규칙을 바꿨다.
- **먼저 쓰기**: AI 설명 전에 내가 2분 먼저 쓴다. 막히면 힌트는 "자리"만 받는다.
- **가르쳐 보기**: 단계 끝마다 내가 설명하고 AI는 채점한다. 채점은 AI 말이 아니라 실행·테스트 같은 **증거**로.
- **질문 주차장**: 질문이 많으면 가장 급한 하나부터, 나머지는 적어 둔다.
- **어려움은 OK, 고통은 X**: 2분 버티고 → 힌트 → 지치면 쉰다. 지쳐서 "몰라"가 나올 때는 아무것도 남지 않았다.

"AI한테 채점을 맡기면 검증을 맡긴 것 아니냐"는 의문도 들었다. 연습의 진짜 일은 **설명을 만들어 내는 것**이고 그건 내가 한다. 채점이 AI 말이면 근거 없는 신뢰이니, 증거로 보여 달라고 했다.

밤 9시 50분, 이 규칙대로 처음 만든 결과:

> **INSERT = 뜻 확인 → id 붙이기 → 파일 끝에 한 줄 쓰기 → B+ 트리에 id → 위치 적기** ✅

빈칸 자리 힌트만 받고 단어는 내가 골랐다. 하루 종일 받아 적은 문장보다 이 한 줄이 더 오래 남을 것 같다.
