## 1. 과제 한 줄 요약

세 단계로 "동작하는 미니 DBMS"를 만든다.

```
Phase 3  API 서버 + 스레드 풀   ← DB 엔진을 바깥에서 쓸 수 있게 감싸기
```

- **"API 서버로 감싼다"**는 오늘 레디스에서 한 일 그대로다. execute_line은 같은 프로그램 안에서만 부를 수 있었는데, server.c로 감싸니 다른 프로세스(nc, bench)가 소켓으로 부를 수 있게 됐다. 감싼다 = 안쪽은 그대로 두고 바깥에서 쓸 수 있는 입구 층을 씌운다.

## 3. 용어: 먼저 내 말로 설명해 보고 검토받았다

외우지 않고 **내 말로 한 줄 + 레디스·PintOS에서 닮은 것**을 짝지었다. 12개 중 6개는 그대로 통과했다.

| 용어 | 내 말 | 보정 | 상태 |
|---|---|---|---|
| DBMS | DB를 read/write. 메모리는 휘발되니 DB에 저장 | 데이터를 디스크(파일)에 오래 보관하고 넣기·찾기를 대신 해 주는 프로그램 | ✅ |
| SQL | DBMS를 조작하는 언어. 자연어에 가깝다 | | ✅ |
| 파싱 | 명령어를 분할? | 자르기 + 조각마다 **이름표** 붙이기 (명령, 테이블, 값) | △ |
| CLI | 키보드로 입력하고 화면에 출력하는 명령줄 인터페이스 | | ✅ |
| 레코드 | 가로 단위 | 가로 한 줄 = 데이터 한 건 (레디스 entry 하나) | ✅ |
| 인덱스 | 세로 단위 ❌ (그건 열) | **찾기를 빠르게 하려고 따로 만든 목차** (id → 레코드 위치) | ❔ |
| B+ 트리 | 모름 | 정렬을 유지하는 나무 모양 **자료구조**. DBMS에서 인덱스 역할 | ❔ |
| 선형 탐색 | 모든 데이터를 하나하나 탐색 | 레디스 체인 따라가기 | ✅ |
| API 서버 | 모름 | 약속된 형식으로 요청을 받아 답하는 서버. **오늘 만든 레디스 서버가 바로 그것** | ❔ |
| 스레드 풀 | 스레드 집합 | **미리** 만든 스레드 여러 개 + **작업 큐** | △ |
| 동시성 문제 | 둘 이상이 같은 데이터를 write하면 race | (하나가 write, 하나가 read해도 생김) | ✅ |

### 테이블과 스키마

```
users 테이블 (= 엑셀 시트 하나)
┌────┬──────┬─────┐
│ id │ name │ age │  ← 스키마 = 머리줄 (열 이름 + 타입)
├────┼──────┼─────┤
│ 1  │ kim  │ 20  │  ← 레코드 (가로 한 줄)
│ 2  │ lee  │ 31  │
└────┴──────┴─────┘
```
✅ **테이블 = 스키마 + (모든) 레코드.**

### 자료구조와 알고리즘

- **자료구조**: 데이터를 어떤 모양으로 담을지 정한 방식 (배열, 연결 리스트, 해시 테이블, 트리)
- **알고리즘**: 그 모양 위에서 일하는 절차. 같은 배열이라도 선형 탐색과 이진 탐색은 속도가 완전히 다르다.
- **B+ 트리의 정체는 자료구조, 역할이 인덱스.** 해시 테이블은 처음부터 순서가 없고(도서관 첫 글자 책장), B+ 트리는 항상 정렬을 지킨다(가나다순 서가). 그래서 범위 찾기도 빠르다.
- 내가 짚은 것: **이번 두 과제의 본질이 자료구조와 알고리즘인데 왜 그렇게 말 안 했나?** 과제 원문이 자료구조 이름을 직접 찍었다 (레디스: 해시 테이블, DBMS: B+ 트리). 자료구조 선택이 속도를 가른다 (레디스 1,000 ms → 0.6 ms, DBMS 100만 번 → 3~4번). 발표의 축은 **"어떤 자료구조를 왜 골랐나"**다.

## 4. SQL 한 줄의 생김새

과제는 INSERT와 SELECT 두 가지만 지원하면 된다.

```sql
INSERT INTO users VALUES ('kim', 20);   -- 넣어라 / users 표에 / 이 값들을
SELECT * FROM users WHERE id = 5;       -- 꺼내라 / 모든 열 / users 표에서 / id가 5인 것만
```

| 레디스 | SQL |
|---|---|
| `SET 날씨 맑음` | `INSERT INTO users VALUES ('kim', 20)` |
| `GET 날씨` | `SELECT * FROM users WHERE id = 5` |
| key 하나 → 값 하나 | 표에 레코드를 넣고, 조건으로 찾음 |

파싱 연습 ✅: `SELECT * FROM books WHERE price = 3000;` → 명령 SELECT, 테이블 books, 조건 price = 3000

핵심 문장 ✅: **테이블(표)에 레코드(가로 한 줄)를 넣고(INSERT), 조건(WHERE)에 맞는 레코드를 찾아 읽는다(SELECT).**

## 5. 인덱스가 없으면 몇 개를 봐야 하나

질문: 레코드 100만 개에서 `id = 777777`을 찾을 때, 인덱스가 없으면 최악의 경우 몇 개를 확인하나?
- 내 답: id가 0부터 차례로 들어 있다고 가정하고 777,778개.
- 보정: 인덱스가 없으면 **순서를 모른다고 봐야 한다.** 그리고 **없는 id**를 찾으면 100만 개를 다 봐야 "없다"고 말할 수 있다. 최악은 **1,000,000개.**
- 내일 Phase 2의 기대값: 선형 탐색 최악 1,000,000개 vs B+ 트리 약 3~4번 ❔

`WHERE age = 31`은? ✅ 인덱스가 id로 정리돼 있으니 age로는 못 쓴다 → 선형 탐색. **id 2는 찾은 결과지 찾는 기준이 아니다.**

## 6. 레코드는 파일에, 인덱스는 메모리에

```
디스크 (파일)   레코드들                          ← 꺼져도 남음
메모리          B+ 트리 인덱스 (id → 레코드 위치)  ← 빨리 찾는 용도, 꺼지면 휘발
```
과제 원문이 "단순화한 메모리 기반"으로 만들라고 한다.

**인덱스가 휘발되면 켤 때는?** 파일의 레코드를 처음부터 끝까지 읽으면서 B+ 트리를 **다시 짓는다.**
- 레디스와 다른 점: 레디스는 꺼지면 데이터 자체가 사라져 복구 불가. DBMS는 원본(파일)이 남아 있어 인덱스를 다시 지을 수 있다.
- 트레이드오프: 메모리 인덱스는 단순하지만 켤 때마다 전부 읽어서 시작이 느리다. 진짜 DBMS는 인덱스도 디스크에 저장해서 켤 때 다시 짓지 않는다. ❔ (Phase 2에서 100만 건 재구축 시간을 재서 확인)

## 7. 큰 그림

```
외부 클라이언트 ──소켓──▶ ┌ Phase 3  API 서버 ──────────────────────────┐
                          │  접수: accept → 요청을 작업 큐에 넣음         │  ← 레디스 server.c
                          │  작업 큐                                      │
                          │  워커 스레드 n개: 큐에서 꺼내 → 엔진 호출      │  ← 새로 (락 필요)
                          └──────────────────┬───────────────────────────┘
                                             │ SQL 한 줄
CLI ──SQL 파일──────────▶ ┌ Phase 1+2  DB 엔진 ─────────────────────────┐
                          │  파서:   SQL → 이름표 (명령, 테이블, 값/조건)  │  ← 레디스 split
                          │  실행기: INSERT / SELECT                     │  ← 레디스 execute_line
                          │    ├ 테이블 파일 (디스크): 레코드들            │  ← 새로
                          │    └ B+ 트리 (메모리): id → 파일 속 위치       │  ← 새로
                          └─────────────────────────────────────────────┘
```
- 레디스와 같은 **계층화**다. 위층은 아래층에 SQL 한 줄만 넘긴다.
- 진짜 새로 배우는 칸은 셋뿐이다: **테이블 파일, B+ 트리, 워커 스레드 n개 + 락.**
- 한 번에 안 외워졌다. 그래서 반복을 세 번 잡았다: 오늘 밤, 화요일 10시, 수요일 발표 준비 전.

### 핵심 구조: INSERT 한 줄의 흐름

```
SQL 파일 → [엔진] 파서 → 실행기 ─┬→ 테이블 파일 끝에 레코드 추가 (id 자동 부여)
                                 └→ B+ 트리에 (id → 파일 속 위치) 등록
```
- 내 답: "SQL 파일을 지나서 DB 엔진에 들어간다" ✅ (바깥 흐름). 엔진 안쪽은 아직 ❔
- **INSERT 하나가 두 곳(파일과 인덱스)을 고친다.** 둘이 어긋나면 인덱스로 찾았는데 엉뚱한 레코드가 나온다. 과제 원문의 "Phase 1과의 매끄러운 연결"이 바로 이 갈림길이다.

## 8. 스레드 풀 = 직원이 여러 명인 은행

레디스는 **직원 1명**이었다 (13일 내 설명: 은행 대기표). 스레드 풀은 직원이 여럿인 은행이다.

| 은행 | 스레드 풀 | PintOS |
|---|---|---|
| 아침에 미리 출근한 창구 직원 4명 | 미리 만든 스레드 4개 | 스레드 |
| 대기표 뽑고 기다리는 손님 줄 | **작업 큐** | ready_list |
| 놀던 직원이 다음 번호를 부름 | 놀던 스레드가 큐에서 꺼내 처리 | |

- 레디스에서 bench가 멈춘 이유: 직원 1명이 말 없는 손님(nc) 앞에서 계속 기다려서, 뒤에 온 bench가 창구에 갈 수조차 없었다. 직원이 4명이면 다른 직원이 bench를 받는다.
- 내 말 ✅: **"요청을 병렬로 처리한다는 것은, 스레드가 반드시 n개라는 것."**
- 직원 4명이 모두 붙잡혀 있으면 다섯 번째 손님은? ✅ 기다린다 (작업 큐에서).

### 트레이드오프: 직원 수 n

- n을 늘리면 기다림이 준다. 대신 메모리가 더 들고, 같은 데이터를 두고 다툴 일(동시성 문제, 락)이 는다.
- 내 생각: 중요한 트레이드오프인데, 직관이 되려면 시간과 노력이 필요하다. → Phase 3에서 n을 1, 2, 4, 8로 바꿔 가며 직접 재 보기로 했다. 직관은 읽어서가 아니라 **재 본 경험**에서 생긴다.
- n은 어림짐작? 반은 맞다. **출발점은 경험칙(CPU 코어 수), 결정은 측정.** 나중에 바꾸기 쉬운 결정이라 빨리 정하고 재면 된다.

## 9. 오늘 배운 일하는 방법

- **용어는 외우지 말고 내 말 + 닮은 것으로 묶는다.** 해시 함수가 도서관 책장으로 붙은 것처럼.

- **한 번에 안 외워지는 건 정상이다.** 반복을 간격을 두고 세 번 잡는다.
- **어색한 문장은 고친다.** "여러 열로 된 가로줄" → "레코드(가로 한 줄)". 외울 문장은 군더더기가 없어야 한다.
