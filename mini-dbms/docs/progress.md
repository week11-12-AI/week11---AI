## 큰 그림 (Claude 초안 ❔, 화요일 아침에 진훈이 확인)
```
Phase 3  API 서버 + 스레드 풀     ← 레디스 server.c 구조 재사용 + 스레드 여러 개
Phase 2  B+ 트리 인덱스 (id)      ← SELECT ... WHERE id = ? 를 빠르게
Phase 1  SQL 처리기               ← SQL 한 줄 → 파싱 → 실행 → 파일에 저장/읽기
```
- 레디스와 같은 계층화: 층마다 아래 층과 함수 하나로만 대화
- 레디스와 닮은 곳: Phase 1의 파싱 = 레디스 계단 2(명령 자르기), Phase 3 = 레디스 계단 3(서버)
- 새로운 곳: SQL 파싱, 파일 저장 형식, B+ 트리, **스레드 여러 개 → 동시성(락)** (레디스는 스레드 1개라 락이 필요 없었음)
- PintOS 연결: 스레드, 락, 세마포어는 PintOS threads에서 이미 본 개념

   - 막힌 곳은 여기에 적고 다음 단계 전에 메운다
   - **11/17 복습 결과 (막힌 곳)**
     1. 서버 시작 4단계: socket(입구) → bind(번호) → listen(준비) → accept(받기). 진훈은 accept부터 답함
     2. 메모장(execute_line의 buf)의 수명 = 명령 하나 → 그래서 깊은 복사. 진훈은 "읽기"라고 답함. "서버 메모리"가 아니라 "메모장"
     3. expire_at = 시각(지금 + TTL). 진훈은 "60을 저장"이라고 답함
     4. entry = 노드 = 데이터 한 건 (같은 것의 세 이름)
     5. 해시 함수 = `hash()` 하나 (key → 칸 번호). ht_set/get/del은 그걸 안에서 쓰는 기능. 진훈은 ht_* 를 해시 함수로 생각함. "왜 쓰나"가 "해시 테이블로 가려고"로 흐려짐 → n개 리스트 중 **정확한 한 리스트로 바로 가려고**
     - 잘한 곳: 서버 루프 두 겹을 버퍼 이동·fd·`\r\n`까지 자세히 / 탈출 조건 / 댕글링·UAF / hashtable 구조체 필드(entry **buckets, size_t n)
