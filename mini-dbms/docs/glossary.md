과제 원문에 나오는 낯선 단어. 외우는 게 아니라 **진훈 말로 한 줄**이 목표.
✅ = 진훈이 자기 말로 설명함 / △ = 반쯤 / ❔ = 아직
"진훈 (11/16)"은 진훈 원문, "보정"은 Claude가 정확도만 고친 것.

## 핵심 문장 (반복해서 말할 것)

| 문장 | 근거 | 날짜 · 상태 |
|---|---|---|
| **테이블 = 스키마 + (모든) 레코드.** 스키마는 머리줄(열 이름 + 타입), 레코드는 가로 한 줄(데이터 한 건) | 진훈 질문 → 확인 | 11/16 ✅ |
| **테이블(표)에 레코드(가로 한 줄)를 넣고(INSERT), 조건(WHERE)에 맞는 레코드를 찾아 읽는다(SELECT).** | 과제 원문 16~23줄 (최소 지원 INSERT, SELECT). 고치기(UPDATE)·지우기(DELETE)는 과제 범위 밖 | 11/16 진훈 문장 다듬음 ✅ |
| **파서는 모양만 보고, 실행기는 뜻을 본다.** 모양 에러(단어 순서·빠진 단어) = 파서, 뜻 에러(없는 테이블·열, 타입 틀림) = 실행기 | 진훈 실험 `INSERT INTO kor …` → 모양은 맞아 파서 통과, 실행기가 `없는 테이블` | 11/17 진훈이 "중요한 명제" 짚음 |
| **인덱스는 그 열(id)로 찾을 때만 쓸 수 있다.** 다른 열(age)로 찾으면 인덱스가 있어도 선형 탐색 | 진훈 추론 (`WHERE age = 31`) | 11/16 ✅ |

## 핵심 구조: INSERT 한 줄의 흐름 (반복할 것)

```
SQL 파일 → [엔진] 파서 → 실행기 ─┬→ 테이블 파일 끝에 레코드 추가 (id 자동 부여)
                                 └→ B+ 트리에 (id → 파일 속 위치) 등록
```
- 왜 중요: INSERT 하나가 **두 곳(파일과 인덱스)**을 고친다. 둘이 어긋나면 인덱스로 찾았는데 엉뚱한 레코드가 나온다.
- 과제 원문 32줄 "레코드가 추가되면 ID가 자동으로 부여되며, 해당 ID를 B+ 트리에 인덱스로 등록", 68줄 "Phase 1과의 매끄러운 연결"이 바로 이 갈림길이다.
- 11/16 진훈: 바깥 흐름 "SQL 파일 → DB 엔진" ✅, 엔진 안쪽은 아직 ❔

## 처음 보는 프로젝트 파악하는 법 (11/17, 외우지 않는다)

1. **폴더 = 종류**: `src` 부품(코드) / `tests` 확인용 코드 / `docs` 기록 / `build` make가 만든 결과물(커밋 안 함)
2. **입구부터 따라가기**: 프로그램은 `main`에서 시작한다. 이 한 줄이 큰 그림이다
   `cli.c main` → `db_execute` (engine.c) → 파서 (sql.c) → 실행기 (engine.c) → 테이블 파일 (table.c)
3. **파일 맨 위 주석**에 역할이 있다. 필요할 때 연다

- 정확한 표현: "**DBMS 프로그램(`./build/dbms`)에 SQL 파일(queries.sql)을 넣어 실행한다**". "DB를 실행한다"는 틀림 (DB는 데이터라서 실행할 수 없다)
- DB = 데이터 (테이블 파일들, 디스크) / DBMS = 그 데이터를 관리하는 프로그램 (컴파일한 실행 파일). 엑셀 파일 ↔ 엑셀 프로그램
- CSV (Comma-Separated Values): 테이블 파일의 저장 형식. 한 줄 = 레코드, 쉼표 = 칸 구분. 글자 값에 쉼표 금지. 줄 길이가 제각각이라 "5번째 줄"로 바로 못 감 → Phase 2에서 B+ 트리에 **바이트 위치**를 저장
- build, data는 커밋 안 함: Git에는 원본만. build는 make로 다시 만들 수 있고, data는 실행 결과물(100만 건이면 수십 MB)

## Phase 1 핵심 로직 (발표에서 설명할 것)

### A. 파서 = 세 문장 (11/17, 문장마다 목격한 증거)
| 문장 | 증거 |
|---|---|
| 1. 첫 단어를 보고 INSERT / SELECT 갈래를 고른다 | `DELETE FROM users;` → `(error) INSERT, SELECT 만 지원` (진훈 예측 ✅) |
| 2. 문법 순서대로 조각을 하나씩 확인하며, 필요한 조각은 sql_stmt 칸에 이름표 붙여 복사한다 | sql_stmt 그림: kind=SELECT, table="users", where_col="id", where_val="2" |
| 3. 순서가 어긋나는 곳에서 바로 에러를 낸다 | `SELECT name FROM users;` → `(error) SELECT 다음에는 * …` |
- sql_stmt = 파서가 모양 검증을 통과시킨 뒤 만든 결과물 = 파서가 실행기에게 건네는 쪽지 (진훈 11/17 ✅)
- 진훈 실험 `WHERE age = 28` → `(0 rows)`: 파서(모양 ✅) → 실행기(age 열 있음 ✅) → 파일 끝까지 읽었는데 28살 없음 (진훈 설명 ✅)
- 파서는 **모양**만 본다. 테이블·열이 있는지, 값 타입이 맞는지는 **실행기**가 본다 (`INSERT INTO kor …` → 실행기의 `(error) 없는 테이블: kor`)

### B. 실행기 INSERT = 세 문장 (Claude 제시, 진훈 확인 전 ❔)
| 문장 | 증거 |
|---|---|
| 1. 스키마를 보고 뜻을 확인한다 (테이블, 값 개수, 타입) | `INSERT INTO kor …` → 없는 테이블 / `VALUES ('kim')` → 값 개수 틀림 |
| 2. id를 붙인다: 켤 때 찾은 가장 큰 id + 1 | 2회 실행이 4부터 / 진훈 실험 choi → id = 7 |
| 3. `id,값,값` 한 줄을 만들어 테이블 파일 끝에 붙인다 | `cat`에서 4,5,6이 끝에 추가 |
- Phase 2에서 추가: 붙인 위치(바이트)를 B+ 트리에 등록

### C. 실행기 SELECT = 세 문장 (진훈 1번 뼈대 + Claude 완성 ❔)
| 문장 | 증거 |
|---|---|
| 1. 스키마를 보고 뜻을 확인한다 (테이블, WHERE 열) | `WHERE age = 28`이 에러 없이 통과 |
| 2. table_scan으로 **테이블 파일**(SQL 파일 아님)을 처음부터 끝까지 한 줄씩 읽는다 | 파일이 늘자 2 rows → 4 rows |
| 3. WHERE 조건에 맞는 줄만 결과에 담고 마지막에 개수를 붙인다 | `WHERE age = 28` → (0 rows) |
- 파일 두 종류: SQL 파일(queries.sql, my.sql = 명령, CLI가 읽음) ↔ 테이블 파일(data/users.csv = 데이터, table_scan이 읽음). 진훈이 헷갈린 곳
- INSERT는 파일 끝에 **쓰고**, SELECT는 파일을 처음부터 **읽는다**

## 부품 7개: 하는 일 / 없으면? (진훈 필기 11/17 ✅)

레디스 짝: server.c ↔ API 서버, command.c ↔ 파서 + 실행기, hashtable.c ↔ 테이블 파일 + B+ 트리 (진훈 답 ✅)

| 부품 | 하는 일 | 없으면? |
|---|---|---|
| CLI | SQL 파일(SQL 문 여러 줄을 적은 텍스트 파일, 과제 13줄)을 읽어서 DB 엔진에 넘긴다 | SQL 파일을 넣을 곳이 없다 |
| 파서 | SQL 1줄을 자르고 이름표를 붙인다 | 실행기가 글자 덩어리만 받아서 무엇을 할지 모른다 |
| 실행기 | 이름표를 보고 테이블 파일(디스크), B+ 트리(메모리)에 일을 시킨다 | 파서 결과가 실행되지 않는다 |
| 테이블 파일 | 레코드 원본을 보관한다. 새 레코드는 **끝에** 붙인다 (id가 항상 제일 크니 저절로 id 순서, 중간에 끼우면 뒤를 전부 밀어 다시 써야 함) | 컴퓨터가 꺼지면 원본 데이터가 휘발된다 |
| B+ 트리 | id로 그 레코드의 파일 속 위치를 알아낸다 | 모든 데이터를 전수조사해야 한다 |
| API 서버 | 소켓으로 외부 요청을 받는다 | 다른 프로그램이 DB를 read/write 할 수 없다 |
| 워커 스레드 n개 | 요청 여러 개를 동시에 처리한다 (최대 n개) | 스레드 1개가 한 요청을 끝낼 때까지 나머지가 기다린다 |

## 인덱스 재구축 (진훈 요청: 따로 정리)

과제의 B+ 트리는 **메모리 기반**(원문 31줄)이라 프로그램이 꺼지면 휘발된다. 레코드 원본은 파일(디스크)에 남는다.

```
프로그램 시작
  테이블 파일의 레코드를 처음부터 끝까지 읽으면서
    레코드 하나마다 → B+ 트리에 (id → 파일 속 위치) 넣기
  다 읽으면 인덱스 완성 → SELECT 받을 준비 끝
```

| | 메모리 인덱스 (우리 과제) | 디스크 인덱스 (진짜 DBMS) |
|---|---|---|
| 꺼지면 | 인덱스 휘발, 레코드는 남음 | 둘 다 남음 |
| 켤 때 | **매번 레코드 전체를 읽어 다시 짓는다** → 100만 건이면 시작이 느림 | 다시 지을 필요 없음. 인덱스 파일에서 **필요한 부분만** 읽는다 |
| 전체를 읽는 때 | 켤 때마다 | 인덱스를 처음 만들 때 한 번 (레코드를 넣을 때마다 인덱스도 같이 고치면 그마저도 없음) |

- 레디스와 다른 점: 레디스는 꺼지면 데이터 자체가 사라져 복구 불가. DBMS는 원본(파일)이 남아 있어 인덱스를 다시 지을 수 있다.
- 발표용 트레이드오프: 메모리 인덱스는 단순하지만 시작이 느리다 ↔ 디스크 인덱스는 시작이 빠르지만 구현이 복잡하다.
