## 핵심 문장 (반복해서 말할 것)

| 문장 | 근거 | 날짜 · 상태 |
|---|---|---|
| **테이블 = 스키마 + (모든) 레코드.** 스키마는 머리줄(열 이름 + 타입), 레코드는 가로 한 줄(데이터 한 건) | 진훈 질문 → 확인 | 11/16 ✅ |
| **테이블(표)에 레코드(가로 한 줄)를 넣고(INSERT), 조건(WHERE)에 맞는 레코드를 찾아 읽는다(SELECT).** | 과제 원문 16~23줄 (최소 지원 INSERT, SELECT). 고치기(UPDATE)·지우기(DELETE)는 과제 범위 밖 | 11/16 진훈 문장 다듬음 ✅ |
| **인덱스는 그 열(id)로 찾을 때만 쓸 수 있다.** 다른 열(age)로 찾으면 인덱스가 있어도 선형 탐색 | 진훈 추론 (`WHERE age = 31`) | 11/16 ✅ |

## 핵심 구조: INSERT 한 줄의 흐름 (반복할 것)

```
SQL 파일 → [엔진] 파서 → 실행기 ─┬→ 테이블 파일 끝에 레코드 추가 (id 자동 부여)
                                 └→ B+ 트리에 (id → 파일 속 위치) 등록
```
- 왜 중요: INSERT 하나가 **두 곳(파일과 인덱스)**을 고친다. 둘이 어긋나면 인덱스로 찾았는데 엉뚱한 레코드가 나온다.
- 과제 원문 32줄 "레코드가 추가되면 ID가 자동으로 부여되며, 해당 ID를 B+ 트리에 인덱스로 등록", 68줄 "Phase 1과의 매끄러운 연결"이 바로 이 갈림길이다.
- 11/16 진훈: 바깥 흐름 "SQL 파일 → DB 엔진" ✅, 엔진 안쪽은 아직 ❔

## 인덱스 재구축 (진훈 요청: 따로 정리)

과제의 B+ 트리는 **메모리 기반**(원문 31줄)이라 프로그램이 꺼지면 휘발된다. 레코드 원본은 파일(디스크)에 남는다.

```
프로그램 시작
  테이블 파일의 레코드를 처음부터 끝까지 읽으면서
    레코드 하나마다 → B+ 트리에 (id → 파일 속 위치) 넣기
  다 읽으면 인덱스 완성 → SELECT 받을 준비 끝
```

| | 메모리 인덱스 (우리 과제) | 디스크 인덱스 (진짜 DBMS) |
|---|---|---|
| 꺼지면 | 인덱스 휘발, 레코드는 남음 | 둘 다 남음 |
| 켤 때 | **매번 레코드 전체를 읽어 다시 짓는다** → 100만 건이면 시작이 느림 | 다시 지을 필요 없음. 인덱스 파일에서 **필요한 부분만** 읽는다 |
| 전체를 읽는 때 | 켤 때마다 | 인덱스를 처음 만들 때 한 번 (레코드를 넣을 때마다 인덱스도 같이 고치면 그마저도 없음) |

- 레디스와 다른 점: 레디스는 꺼지면 데이터 자체가 사라져 복구 불가. DBMS는 원본(파일)이 남아 있어 인덱스를 다시 지을 수 있다.
- 발표용 트레이드오프: 메모리 인덱스는 단순하지만 시작이 느리다 ↔ 디스크 인덱스는 시작이 빠르지만 구현이 복잡하다.
- 11/16 Claude 정리 ❔ (Phase 2에서 100만 건 재구축 시간을 재서 확인)

## 용어

| 용어 | 진훈 (11/16) | 보정 | 레디스·PintOS에서 닮은 것 | 상태 |
|---|---|---|---|---|
| 자료구조 | | 데이터를 메모리에 **어떤 모양으로 담을지** 정한 방식 (배열, 연결 리스트, 해시 테이블, 트리) | 레디스 = 해시 테이블 | ❔ |
| 알고리즘 | | 그 모양 위에서 **일하는 절차** (찾기, 넣기, 지우기) | 레디스 find (칸 고르기 → 체인 따라가기) | ❔ |
| DBMS | 데이터베이스 관리 시스템. DB를 read/write. 메모리는 휘발되니 DB에 저장 | 데이터를 **디스크(파일)에 오래 보관**하고, 넣기·찾기를 대신 해 주는 프로그램 | 레디스는 메모리라 꺼지면 휘발 ↔ DBMS는 파일이라 남음 | ✅ |
| SQL | DBMS를 조작하는 언어. 자연어에 가깝다 | | 레디스 명령(`SET`/`GET`)의 DBMS판 | ✅ |
| 파싱 | 명령어를 분할? | 분할 + **구조화**: 자르고, 각 조각이 무엇인지(명령, 테이블 이름, 값) 이름표를 붙여 담기 | 레디스 split → argv[0] 명령, argv[1] key | △ |
| CLI | 명령줄 인터페이스. 키보드로 입력하고 화면에 출력 | | 터미널에서 `./build/server` 친 것 | ✅ |
| 테이블 | 데이터가 저장된 구조 → "테이블 = 스키마 + (모든) 레코드" ✅ | **표.** 엑셀 시트 하나 | | ✅ |
| 스키마 | (테이블과 같이 답함) | **표의 설계도.** 열 이름과 타입 (예: id 정수, name 글자). 과제는 "이미 있다고 가정" | | △ |
| 레코드 (행) | 구조의 가로 단위 | 가로 한 줄 = 데이터 한 건 | 레디스 entry 하나 | ✅ |
| 필드 (열) | | 세로 한 칸 = 항목 하나 (id, name, age) | | ❔ |
| 인덱스 | 구조의 세로 단위 ❌ (그건 열) | **찾기를 빠르게 하려고 따로 만든 목차.** 데이터와 별개로 "id → 그 레코드의 위치"를 정리해 둔 것 | 도서관 책장 규칙, 해시 테이블 | ❔ |
| B+ 트리 | 모름 | **자료구조**(나무 모양). DBMS에서 **인덱스 역할**을 맡는다. 항상 **정렬된 순서**를 유지해서 범위 찾기도 빠르다 (세부는 화요일) | 해시 테이블은 순서 없음 ↔ B+ 트리는 순서 있음 | ❔ |
| 선형 탐색 | 모든 데이터를 하나하나 탐색 | | 레디스 체인 따라가기 (find) | ✅ |
| API 서버 | 모름 | 약속된 형식으로 요청을 받아 답하는 서버 | **오늘 만든 레디스 서버가 바로 API 서버** | ❔ |
| 스레드 풀 | 스레드 집합 | 미리 만들어 둔 스레드 여러 개 + **작업 큐**(처리 안 된 요청들의 줄). 요청이 오면 놀고 있는 스레드가 큐에서 꺼내 처리. 은행: 창구 직원 여럿 + 대기표 줄 | PintOS 스레드, ready_list | △ |
| 동시성 문제 | 특정 데이터를 2개 이상의 주체가 write 하면 race 문제 | (하나가 write, 다른 하나가 read 해도 생김) | PintOS 락. 레디스는 스레드 1개라 없었음 | ✅ |
