# mini-dbms

C로 직접 만든 작은 DBMS입니다. SQL 처리기, B+ 트리 인덱스, 스레드 풀 HTTP API 서버로 이루어져 있습니다.
외부 라이브러리 없이 C11 표준 라이브러리, POSIX 소켓, pthread만 사용했습니다.

```
            ┌───────────── 입구 ─────────────┐
 SQL 파일 → │ CLI (build/dbms)                │
 HTTP     → │ API 서버 (build/server)         │  accept → 작업 큐 → 워커 스레드 n개
            └───────────────┬────────────────┘
                            │ db_execute(sql) → 결과 글자     (엔진 잠금 하나)
            ┌───────────────▼──────── DB 엔진 ─┐
            │ 파서 (sql.c)    : 형식 검증, SQL → sql_stmt          │
            │ 실행기 (engine.c): 내용 검증 (스키마), INSERT / SELECT │
            │   ├ 테이블 파일 (table.c)  : 디스크, CSV, 끝에 추가     │
            │   └ B+ 트리 (bptree.c)     : 메모리, id → 바이트 위치  │
            └──────────────────────────────────┘
```

| 단계 | 내용 |
|---|---|
| Phase 1 | SQL 파서 + 실행기, 테이블 = CSV 파일 하나, CLI로 SQL 파일 실행 |
| Phase 2 | 메모리 B+ 트리로 id 인덱스, 자동 id, 100만 건에서 인덱스 사용/미사용 비교 |
| Phase 3 | HTTP API 서버, 고정 크기 스레드 풀 + 작업 큐, 엔진 잠금, 정상 종료 |

## 빌드와 실행

Linux(또는 WSL)에서 gcc와 make가 필요합니다.

```bash
make all                                   # build/dbms, build/server, build/bench

# Phase 1: SQL 파일을 CLI로
./build/dbms queries.sql                   # 데이터는 data/users.csv

# Phase 3: API 서버
./build/server -p 8080 -t 4 -d data        # 포트, 워커 수, 데이터 폴더
curl -X POST --data-binary "INSERT INTO users VALUES ('kim', 31);" http://127.0.0.1:8080/query
curl -X POST --data-binary "SELECT * FROM users WHERE id = 1;"     http://127.0.0.1:8080/query
```

### SQL

```sql
INSERT INTO users VALUES ('kim', 31);      -- id 는 자동 (가장 큰 id + 1)
SELECT * FROM users;
SELECT * FROM users WHERE id = 1;          -- B+ 트리
SELECT * FROM users WHERE name = 'kim';    -- 선형 탐색
```

- 테이블은 `users(id 정수, name 글자, age 정수)` 하나이고, 스키마는 코드에 정의되어 있습니다. 과제 조건이 "schema와 table은 이미 존재한다고 가정"입니다.
- 키워드는 대소문자를 구분하지 않고, 끝의 `;`는 생략할 수 있습니다. 비교는 `=` 하나만 지원합니다.

### HTTP API

| 요청 | 응답 |
|---|---|
| `POST /query` (본문 = SQL 한 문장) | 200 결과 / 400 SQL 에러 |
| `GET /health` | 200 `ok` |
| 그 밖 | 404 경로 없음, 405 메서드, 411 Content-Length 없음, 413 너무 큼, 503 대기열 가득 |

## 설계 결정

**파서는 형식, 실행기는 내용.** 파서(`sql.c`)는 단어 순서와 값의 모양만 봅니다. 테이블과 열이 있는지, 타입이 맞는지는 실행기가 스키마를 보고 판단합니다. 예를 들어 `INSERT INTO kor VALUES ('a', 1)`은 파서를 통과하고 실행기에서 "없는 테이블"이 됩니다. 둘을 나눈 덕분에 파서는 파일이나 엔진 없이 단독으로 테스트할 수 있습니다(`tests/test_sql.c`).

**테이블 파일 = CSV, 끝에만 추가.** 레코드 한 줄이 곧 CSV 한 줄입니다. 새 id는 항상 가장 크기 때문에 끝에 붙이면 파일이 저절로 id 순서가 되고, 기존 내용을 옮길 일이 없습니다. 그래서 글자 값에는 쉼표와 줄바꿈을 쓸 수 없게 막았습니다.

**B+ 트리 = 메모리 목차, 켤 때 재구축.** 줄 길이가 제각각이라 "n번째 줄"로 바로 갈 수 없습니다. 그래서 트리는 `id → 파일 속 바이트 위치`를 저장하고, 찾은 위치로 `fseek`해서 한 줄만 읽습니다. 노드 하나가 최대 63개의 key를 담아서 100만 건에서도 높이가 4입니다. 트리는 메모리에 있어 꺼지면 사라지지만, 원본 파일이 남아 있으므로 켤 때 파일을 한 번 훑어 다시 짓습니다. 이 재구축 비용(100만 건 약 1.2초)이 메모리 인덱스의 트레이드오프입니다.

**스레드 풀 + 엔진 잠금 하나.** 메인 스레드는 `accept`만 하고, 연결을 크기 64의 원형 작업 큐에 넣습니다. 워커 n개가 조건 변수로 잠들어 있다가 하나씩 꺼내 처리합니다. 큐가 가득 차면 기다리게 하지 않고 바로 503을 돌려줍니다. 엔진은 파일 위치, 트리, 다음 id를 함께 쓰기 때문에 `db_execute` 안의 뮤텍스 하나로 보호합니다. 네트워크 입출력과 SQL 파싱은 잠금 밖에서 병렬로 돌고, 실행만 한 번에 하나씩입니다. 단순하고 정확한 대신 SELECT끼리도 동시에 실행되지 않는 것이 한계입니다.

**쓰기 버퍼: 대량 넣기는 모아서, 서버는 바로.** 처음에는 INSERT마다 `fflush`를 해서 2만 건에 17초가 걸렸습니다. 파일 크기를 직접 세어 `fseek`/`fflush`를 없애고 버퍼에 모아 쓰자 0.2초로 줄었습니다. 서버는 "응답한 INSERT는 서버가 죽어도 남아야 한다"는 기준으로 `db_set_sync(1)`을 켜서 INSERT마다 내보냅니다.

## 성능 (100만 건)

`N=1000000 bash tests/func_phase2.sh`, WSL2 Ubuntu, `-O2`, Windows 디스크(/mnt/c). 한 번 측정한 값입니다.

| 측정 | 결과 |
|---|---|
| INSERT 100만 건 (SQL 문자열 → 파서 → 실행기) | 3.6초 |
| 켜기 (파일 훑기 + 인덱스 재구축) | 1,186 ms |
| `WHERE id = 500000`, **인덱스 사용** | **0.307 ms** |
| `WHERE id = 500000`, 인덱스 미사용 (선형 탐색) | 1,160 ms (**약 3,800배**) |
| `WHERE name = 'user500000'` (선형 탐색) | 1,289 ms |
| B+ 트리 높이 | 4 |

같은 SQL을 인덱스만 끄고(`db_set_use_index(0)`) 다시 재서, 차이가 오직 탐색 방법에서 온다는 것을 확인했습니다.

```bash
make test          # 단위 테스트 73개 (ASan + UBSan)
make functional    # 기능 테스트 26개 (Phase 1·2·3)
make check         # 둘 다
```

| 종류 | 파일 | 확인하는 것 |
|---|---|---|
| 단위: 파서 | `tests/test_sql.c` (26) | 정상 문법, 모양 에러 16종, 이름·값 길이 경계 |
| 단위: B+ 트리 | `tests/test_bptree.c` (8) | 100만 개를 섞인 순서로 넣고 전부 찾기, 없는 key, 높이 |
| 단위: 엔진 | `tests/test_engine.c` (39) | INSERT/SELECT, 재시작 후 id 이어짐, 인덱스 끈 결과도 같음, 망가진 파일, 스레드 8개 동시 INSERT |
| 기능: Phase 1 | `tests/func_phase1.sh` (5) | SQL 파일 실행 출력이 `tests/phase1.expected`와 글자까지 같음, 파일 내용, 재실행 |
| 기능: Phase 2 | `tests/func_phase2.sh` (3) | 대량 INSERT 후 세 가지 검색이 같은 답, 인덱스가 10배 이상 빠름 |
| 기능: Phase 3 | `tests/func_phase3.sh` (18) | 실제 서버 + curl: 정상, 400/404/405/411/413, 동시 400건 id 중복 없음, 재시작 후 데이터 유지, SIGTERM 정상 종료 |

**다룬 엣지 케이스**: 빈 SQL, 따옴표 안 닫힘, 두 문장, 문장 뒤 쓰레기, 최대 길이 넘는 이름과 값, 정수 범위 넘침, 값 속 쉼표와 줄바꿈, 빈 글자 값, 음수, `022`와 `22`를 같은 수로 비교, 대소문자 다른 테이블·열 이름, 빈 줄·깨진 줄·끝 줄바꿈 없는 테이블 파일, 실패한 INSERT가 id를 소모하지 않음, Content-Length 없음과 잘못된 값, 너무 큰 요청, 응답 전에 끊긴 연결(SIGPIPE 무시), 멈춘 클라이언트(읽기 5초 제한).

## 한계

- 테이블 하나, `SELECT *`만, 비교는 `=` 하나. UPDATE/DELETE, 범위 조건, JOIN은 없습니다.
- 인덱스는 id 하나뿐입니다. 다른 열 검색은 선형 탐색입니다.
- 엔진 전체가 잠금 하나라서 읽기끼리도 동시에 실행되지 않습니다. 읽기-쓰기 잠금이나 테이블별 잠금이 다음 단계입니다.
- 글자 값에 작은따옴표를 넣는 방법(이스케이프)이 없습니다.
- 인덱스가 메모리에만 있어서 켤 때마다 재구축합니다.
